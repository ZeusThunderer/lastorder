# lo-review — проверить задачу

Если ты не Claude Code (supervisor) — остановись, этот скил не для тебя.

Протокол и чек-лист: `docs/agents/coop-protocol.md`, разделы «Ревью», «Критичные зоны» и
«Worktree и merge». Шаблон: `docs/agents/work/_templates/review.md`.

Режим по умолчанию — `result`. Режим `answer` — ниже.

Корень репозитория — `main`, ветку в нём не переключаешь. Задача проверяется в её worktree:
`wt=$(bash dev/task_worktree.sh T-NNN --attach)`. Если тебя вызвали headless, ты уже в нём.

## Шаги (result)
1. Статус: `bash dev/tasks.sh` (истина — копия `task.md` в ветке). Нужен `review`. Иначе сообщи
   пользователю и остановись.
2. Открой worktree (`--attach`) и проверь, что он чистый (`git -C "$wt" status --short`).
   Незакоммиченные правки исполнителя — не твои: сообщи и остановись.
3. Прочитай в worktree `task.md`, последний раунд `report.md` и прошлые раунды `review.md`.
4. `git log main..<branch>` и `git diff main...<branch>`. Прочитай каждый изменённый файл
   в контексте, а не только diff. Задачу с `criticality: critical` или с diff в критичной зоне
   проверяешь построчно.
5. В worktree сам прогони `bash dev/check.sh` и команды из «Проверок».
   Отчёту не верь на слово: расхождение с отчётом — находка уровня blocker.
6. Пройди критерии приёмки и чек-лист проекта из протокола. Проверь, что изменения не вышли за
   «Можно трогать».
7. Ответы `disputed` из отчёта: прими или подтверди находку с доводом.
8. Находки с очевидной правкой до ~20 строк в сумме, без выбора решения, исправь сам через
   `lo-direct-edit` (основание 5): правка в worktree, проверки заново, в раунде — `fixed by supervisor
   <sha>`. Такие находки не дают `changes`. Остальные — ZCode.
   Допиши раунд в `review.md` в worktree (создай файл из шаблона, если его нет). Вердикт:
   - `accept` — нет открытых blocker и major;
   - `changes` — есть хотя бы одна;
   - `reject` — неверна сама постановка: перепиши `task.md`, верни статус `ready`.
9. Если та же находка не закрыта второй раунд подряд — можно исправить самому через `lo-direct-edit`
   (основание 2). Это не обязательно: сначала подумай, не яснее ли переформулировать находку.
10. Поставь статус в `task.md` worktree: `accepted`, `changes` или `ready` (при reject). Закоммить вместе
    с `review.md`: `T-NNN: review round N`, трейлер `Agent: claude`.
11. При `accept`: `bash dev/merge_task.sh T-NNN`. Скрипт:
    - вливает `main` в ветку и повторяет проверки;
    - под блокировкой мержит `--no-ff` в `main`;
    - ставит `done` и обновляет BOARD.
    Если скрипт отказал из-за конфликта с `main` или красных проверок после слияния:
    - допиши в `review.md` находку `R<N>-<k> · blocker · подтянуть main`;
    - верни статус `changes` коммитом в worktree.
    Затем:
    - пункт `prototype-plan.md`, если задача его закрывает, отметь через
      `bash dev/on_main.sh git commit …` после правки в корне;
    - `bash dev/tasks.sh --prune` уберёт worktree и ветку.
12. При `changes` или `reject`: `bash dev/tasks.sh --sync`, чтобы BOARD совпал со статусом.
    Скажи пользователю одной строкой, что передать ZCode: «доработай T-NNN».

Мерж — только через `merge_task.sh`, без ручного `git merge` в корне. Push в remote — только
если пользователь попросил.

## Режим answer
Исполнитель задал вопрос: статус `blocked`, вопросы — в разделе «Вопросы» последнего раунда
`report.md`, причина — строка `Blocked:` в `task.md`.
1. Открой worktree (`--attach`). Прочитай `task.md`, вопросы и то, что уже сделано (`git diff main...HEAD`).
2. Реши, входит ли вопрос в «Эскалацию оператору» протокола. Входит — `Blocked: нужен оператор — <причина>`,
   вердикт `blocked`. Нет — отвечаешь сам.
3. Допиши в `review.md` раздел `## Ответ N · YYYY-MM-DD` с ответом на каждый вопрос. Если ответ
   меняет постановку, поправь `task.md`: критерии, «Можно трогать», «Заметки надзора».
4. Убери строку `Blocked:`, поставь `status: in_progress`. Закоммить в worktree: `T-NNN: answer N`,
   трейлер `Agent: claude`. Вердикт `answered`.

## Headless
Применяется, когда тебя вызвал ZCode через `dev/call_supervisor.sh`, а не оператор. Ты запущен
в worktree задачи, скрипт уже проверил лимит вызовов. Оператора нет, и решаешь ты: к нему идёт
только список «Эскалация оператору» из протокола.
- Корень репозитория назван в промпте. Этот скил, протокол и CLAUDE.md читай из корня, скрипты
  `dev/` запускай оттуда же (`bash <корень>/dev/merge_task.sh T-NNN`): копии в ветке могут быть
  старше `main`.
- В заголовок раздела допиши `· headless`: `## Раунд N · … · вердикт: … · headless`,
  `## Ответ N · … · headless`. По этим пометкам скрипт считает лимит.
- Критичную задачу проверяешь построчно (шаг 4) и по чек-листу проекта без послаблений: фильтр
  сырых id, путь смерти и аварийное завещание, единственный писатель базы, уровни LLM.
- Вердикты `accept`, `changes`, `reject` и разбор `disputed` — твои. При `reject` перепиши `task.md`
  и поставь `ready`.
- Прямая правка по основаниям 1–3 и 5 — через `lo-direct-edit`, как обычно: D-NNN в DIRECT_EDITS
  (`bash <корень>/dev/on_main.sh …`), строка в «Заметках надзора». После правки прогони проверки
  и вынеси вердикт.
- Стенд: проверки из задачи с `docker compose` прогоняешь сам, под `bash <корень>/dev/stand.sh lock T-NNN`
  (занято — проверку не прогоняешь, пишешь «стенд занят T-MMM» и решаешь по остальному; в конце `unlock`). `down`, `docker volume` и
  `docker system` запрещены, мир стенда не сбрасываешь. Стенд не поднялся — находка в раунде,
  вердикт `changes` или `blocked` по существу. Команду, которую не дают запустить права,
  считай непройденной.
- Эскалация (`blocked`): `status: blocked`, строка `Blocked: нужен оператор — <причина>`.
- `accept` — тот же `merge_task.sh`, что и в шаге 11. Worktree остаётся на месте, его уберёт
  `tasks.sh --prune`.
- Без `git push`, `reset`, `clean`, `rebase`, без `git switch` в корне.
- Последняя строка ответа: `VERDICT: accept | changes | reject | answered | blocked`.
