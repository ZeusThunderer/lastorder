## ADR-001. Контуры с разной частотой

**Контекст.** Игре нужны реакции за десятки миллисекунд, чату — за секунды, памяти — за минуты.
Один сеанс `aw` идёт десятки секунд и не годится для реального времени
[проверено: aw/tools/compose_session.py, aw/agent/scripts/sleep.sh].

**Решение.** Пять контуров: C0 рефлекс, C1 тактика, C2 стратегия, C3 соцконтур, C4 рефлексия.
Параметры и арбитраж — ARCHITECTURE §3–4.

**Альтернативы.** Один агент с инструментами (так `nt`: ~7k токенов, перегрузка инструментами
[проверено: nt/docs/agent_plan.md]); последовательный мультиагент (тоже `nt`
[проверено: nt/src/agent/multiagent.py]).

**Последствия.** Нужны шина, общее состояние и правила владения телом.

## ADR-002. Форк `aw`

**Контекст.** `aw` — шаблон, задуманный для форка [проверено: aw/README.md]. Менять его можно.
Как submodule он не работает: `compose_session.py` ищет персонажей рядом с собой
[проверено: aw/tools/compose_session.py, `ROOT`/`AGENTS`].

**Решение.** Форк; upstream-remote; правки отдельными коммитами `aw-fix:` (безопасность и
баги) и `aw-ext:` (расширения). Новый код — в `runtime/`.

**Что правим.** Проверка аргументов в скриптах (обход через `../../PERSONA` в `remember.sh`
[проверено: aw/agent/scripts/remember.sh]); лимит и ISO-время в `unanswered()`; секция
`--live`; жёсткий лимит `state.md` в `check.py`.

**Откат.** Ветка без правок `aw-ext:`.

## ADR-003. Исполнитель — `uc`

**Контекст.** Стек курса — Fabric 1.21.11 + `uc` [проверено: uc/README.md; course.personalabs.ru/instructions/minecraft].
PoC работает на Mineflayer 1.16.5 [проверено: mca/package.json, mca/optimization/nether/config.json]
и не виден на стриме как нативный клиент.

**Решение.** Тело — `uc` через Py4J; MCP — для отладки и стратега. Варианты для C1 — это
altoclef-команды (`@get`, `@goto`, `@stop`, `@gamer`) и небольшой набор рычагов
[проверено: uc/docs/features/AGENT_PY4J_LEVERS.md]. Собственные навыки по образцу
`mca/nether-agent.mjs` не пишем.

**Что берём из PoC:** паттерн «код генерирует варианты → Jev выбирает», `bounded()` с таймаутом,
кулдаун после неудачи, журнал `events.jsonl`, проверки прогона.
**Что не берём:** координаты сида, мирную сложность, серверный сенсор дракона, заранее
разведанный маршрут.

**Риск.** `@gamer` оценён 2/5, End не достигнут, бывают простои по несколько минут
[проверено: uc/README.md, uc/docs/STATUS-2026-09-14.md]. Отсюда сторож простоя в C1.

## ADR-004. FastJev в C1 (D2)

**Контекст.** Jev от TypeSafe — закрытая модель решений, ~300 мс через API. FastJev — открытая
MIT-реализация того же интерфейса; Qwen3.5-4B, медиана 83 мс на 3 решения через vLLM
[проверено: README fastjev 0.2.0 на PyPI]. В PoC Jev выбирал макро-действия раз в ~4 с,
скорость давали маршрут и навыки [проверено: mca/nether-agent.mjs; расчёт по mca/README.md].

**Решение.** `FastJevDecider` локально на 5070 Ti; `TypeSafeJevDecider` через OpenRouter
(`typesafe/jev-1.13` [проверено: mca/models.mjs]) — эталон для A/B на одних и тех же состояниях.

**Даёт:** решение быстрее 150 мс, вероятности для комментария.
**Стоит:** 4–9 ГБ VRAM, новая зависимость; вероятности надо калибровать на своих логах.
**Откат:** `RuleDecider` → `@gamer`.

## ADR-005. Свой арбитр; `nt` не используется (D1)

**Контекст.** `nt` — прототип другого трека курса. Его цикл последовательный
(3 реакции → 1 план) [проверено: nt/src/agent/multiagent.py].

**Решение.** Свой арбитр и адаптеры к готовым библиотекам (TwitchIO, pyvts, obsws-python,
Pipecat). Из `nt` берём идеи: колбэки Py4J как источник событий, фильтр спама чата,
группы инструментов, ≤3 человека в контексте.

**Откат.** Стек курса за теми же портами.

## ADR-006. Redis Streams (D3)

**Решение.** Шина на Redis Streams, общее состояние — ключи Redis с одним писателем.
**Альтернативы.** asyncio в одном процессе (падение одного роняет всех); ZeroMQ/NATS (новая
зависимость). **Откат.** Очереди в памяти одного процесса.

## ADR-007. Python на Windows, инференс в WSL (D7)

**Контекст.** `nt` советует запускать Python-часть в Windows, не в WSL, из-за звука
[проверено: nt/README.md]. Py4J требует колбэк-сервер, в который ходит Java
[проверено: uc/…/PythonCallback.java]. Клиент Minecraft, OBS и VTube Studio — на Windows.

**Решение.** `runtime/` на Windows; FastJev, локальная LLM, Redis, Mem0 и раннер C4 — в Docker
на WSL2 с привязкой к картам через `device_ids`.
**Откат.** Всё на Windows нативно.

## ADR-008. Pipecat (D4)

**Решение.** Голосовой цикл C3 на Pipecat (BSD-2): пайплайн кадров, прерывания, VAD, метрики
[источник: сравнения Pipecat/LiveKit, 2026].
**Альтернативы.** LiveKit Agents (рассчитан на WebRTC-комнаты); свой asyncio-цикл.
**Риск.** Вывод на VB-Cable и вход по нескольким игрокам — [предположение], этапы 3–4.
**Откат.** Свой asyncio-цикл.

## ADR-009. Silero TTS, A/B с CosyVoice3 (D5)

**Решение.** Silero v5 на CPU по умолчанию (готовые русские голоса, автоударения);
CosyVoice3 на 2070 — кандидат (потоковый режим, заявлено ~150 мс) [источник: Хабр; qvib.pro].
Лицензии Silero и XTTS некоммерческие — для учебного проекта подходят.
**Откат.** Fish TTS из стека курса.

## ADR-010. GigaAM v3 для голоса игроков (D8)

**Контекст.** `uc` уже отдаёт голос каждого игрока в Python: `onVoiceFeed(playerName, PCM16LE)`
[проверено: uc/…/util/agent/VoiceChatIntegration.java]. Очередь на 32 пакета, один поток,
старые пакеты выбрасываются; раньше переполнение роняло JVM [проверено: uc/…/Py4jEntryPoint.java].

**Решение.** VAD-сегментация отдельно по каждому игроку → пакетная расшифровка GigaAM v3 на CPU.
WER на русском лучше Whisper turbo и Parakeet на сложных доменах, RTF ≈ 0.05 на CPU
[источник: stt-ru-benchmark; Хабр].
**Альтернативы.** Потоковый GigaAM (gigastt: первое слово 0.8–1.65 с, WER хуже);
Parakeet / Whisper на GPU.
**Риск.** Голос нагружает тот же Py4J, что и управление, — мерить на этапе 0.
**Откат.** Parakeet в контейнере по инструкции курса.

## ADR-011. Память: Mem0 + файлы `aw` (D6)

**Решение.** Быстрые факты о людях — Mem0 (Apache-2.0, `add()`/`search()` по человеку)
[источник: сравнения Mem0/Letta/Graphiti]; отобранное — `entities/` в `aw`, пишет C4.
Единая модель `person` для зрителей и игроков.
**Альтернативы.** Только файлы (медленно); Graphiti + FalkorDB (временной граф, тяжелее);
Letta (заменяет рантайм).
**Откат.** Только файлы `aw`.

## ADR-012. Чат и голос не влияют на игру

**Решение.** C1 и C2 не подписаны на `ev.chat` и `ev.voice`. Персонаж реагирует на сообщения
словами, как стример, но игровых решений по ним не принимает.
**Последствие.** Инъекция из чата в игру невозможна по построению.

## ADR-013. Whitelist серверов и профили

**Решение.** Список хостов в конфиге; вне списка бот только наблюдает. Профиль `local` с
RCON-метриками, `public-safe` для остальных хостов из списка.
**Источник данных.** `onUpdateServerInfo` / `getServerInfoDict` [проверено: uc/…/Py4jEntryPoint.java].

## ADR-014. VLA не используем

**Решение.** VLA исключены на текущем этапе. Лучшие открытые модели для Minecraft
(JARVIS-VLA) работают на 5.5–8 FPS и в симуляторе MineStudio, а не в клиенте курса
[источник: arXiv 2503.16365; README JarvisVLA].
**Пересмотр.** После этапа 8, если останется ресурс.

## ADR-015. Всё в Docker (2026-10-14)

**Контекст.** ADR-007 оставлял Python на Windows ради звука и колбэка Py4J. На первом этапе звука
нет: Telegram, голос и стрим идут после 1–2 итерации разума. Нужны 2–3 клиента Minecraft,
воспроизводимые и изолированные. Py4J в uc слушает только localhost [проверено: uc/AltoClef.java,
GatewayServer без адреса].

**Решение.** `mc-server` (itzg), `body-N` (HeadlessMC + Fabric 1.21.11 + jar uc, без рендера),
`mind-N` в сетевом пространстве своего тела (`network_mode: service:body-N`), `hive`, локальная LLM
(vLLM) по профилю. Схема — docs/agents/docker-topology.md.

**Альтернативы.** Образ `mineswarm-mc` из стенда uc — его исходников у нас нет. Клиенты на Windows —
не масштабируются до 3 и не изолированы.

**Последствия.** Нет экрана: на стрим понадобится отдельное тело с рендером (Xvfb/llvmpipe или Windows).
GPU свободен для LLM. **Риск:** uc без OpenGL может не стартовать — спайк E1, запасной путь — Xvfb + llvmpipe.
**Откат.** ADR-007 для мозгов, клиенты на хосте.

## ADR-016. Сеть сразу (2026-10-14)

**Решение.** Первый этап — 2–3 узла в одном постоянном мире: живут, ротируются, оставляют завещания,
пополняют общую базу. Отдельной эстафеты одного узла нет; её критерий входит в критерий MVP
(docs/agents/prototype-plan.md). ROADMAP этап 0 (скорость, FastJev) отложен: MVP — медленный LLM-цикл
раз в 8–15 с за портами `GameBody` / `PersonaProvider` / `Memory`, чтобы C1 и FastJev встали потом
без переписывания.

## ADR-017. Память сети «Мисака-нет» (2026-10-14)

**Решение.** Общая база знаний сети плюс своя память узла: слои, формат записи, согласование —
[KNOWLEDGE.md](KNOWLEDGE.md). Пишет в базу только hive (файлы на volume под git, ради истории и `blame`).
Узлы шлют кандидатов и голосуют попутно в обычном шаге. Знание в контексте — не приказ (бриф §1).
**Альтернативы.** «Git-сознание»: ветки узлов, сновидец сливает в main — отложено, формат записи его
не исключает. Mem0/векторный RAG на старте — избыточно: знания привязаны к handle-ам восприятия.

## ADR-018. Слот и узел; имя узла — пресет (2026-10-14)

**Решение.** Слот — постоянная пара тело + мозг с аккаунтом `LastOrder01..03`. Узел — личность внутри
слота со сквозным 5-значным номером из hive; после смерти в том же слоте рождается следующий.
Имя и манера речи — пресет в конфиге, выбор не окончательный:
- `lab` (по умолчанию, как в брифе и task1): «узел 00007», первое лицо, без родовых окончаний;
- `misaka`: «Мисака 00007», реплика как зачитанная из книги, третье лицо («…, сказала Мисака 00007»).

**Последствия.** Шаблон промпта получает плейсхолдеры `{node_name}` и `{speech_style}`; task1.md не меняется.


## ADR-019. Два кодинговых агента: ZCode исполняет, Claude проверяет (2026-10-16)

**Изменено ADR-028 и ADR-040:** задачи передаёт не человек, а ZCode сам вызывает headless-Claude; субагентов нет.

**Решение.** Код пишет ZCode (worker), Claude Code ставит задачи, проверяет и мержит (supervisor).
- Обмен — файлы в git (`docs/agents/work/T-NNN-*/task.md|report.md|review.md`); задачи между
  харнессами передаёт человек.
- Одна задача — одна ветка `z/T-NNN-<slug>` и свой worktree `.worktrees/T-NNN-<slug>`: задачи идут
  параллельно, корень всегда на `main`. В `main` ZCode не коммитит, merge — скриптом под блокировкой.
- Claude правит код сам только по четырём основаниям: критичная зона, два раунда без исправления,
  блокер, приёмочный тест-контракт. Каждая правка — запись `D-NNN` в `docs/agents/work/DIRECT_EDITS.md`
  и трейлер `Agent: claude-direct`.
- Правила проекта одни на двоих — CLAUDE.md. Корневой `AGENTS.md` для ZCode ссылается на него,
  не копирует. Скилы: `.claude/skills/` (Claude), `.zcode/skills/` (ZCode).
- Для некритичных задач ZCode по своему решению вызывает Claude Code CLI headless (Opus, effort medium)
  через `dev/call_supervisor.sh`: проверка плана или результата без оператора. Скрипт не пускает
  критичные задачи и ограничивает число раундов. (Изменено ADR-028: критичные задачи тоже идут headless.) Headless-Claude код не правит, а спорное передаёт
  оператору (`blocked`).

**Последствия.** Детали — `docs/agents/coop-protocol.md`. Отчёт исполнителя не принимается на слово:
проверки надзор прогоняет сам. Пути скилов ZCode взяты из сторонних обзоров; если ZCode их не видит,
скилы переезжают в `.claude/skills/` (роль указана в описании каждого скила).

## ADR-020. Восприятие `plain` по умолчанию; основы игры — стартовая база сети (2026-10-16)

**Контекст.** Маскировка (handle + описание) требует таблицы описаний, которую заполняет человек, и
мешает узлу играть: он не может опереться ни на что, кроме своих проб. Решение пользователя 2026-10-16:
«пока не маскировать, передать сети основы игры как базовые знания».

**Решение.**
- Режим `PERCEPTION_MODE=plain|masked`, по умолчанию `plain`.
  - `plain`: имена игры идут в промпт в нормализованном виде (без `minecraft:`, единый регистр).
  - `masked`: поведение E0 — handle + описание/термин; тест на утечки сырых id действует в этом режиме.
- В обоих режимах служебные строки uc (`[Alto Clef]`, `[Tungsten]` и подобные) в промпт не попадают.
- Основы игры — **праймер**: стартовые записи общей базы (автор `primer`, статус `confirmed`) в формате
  KNOWLEDGE.md §2. Компактный, курируемый, с бюджетом токенов. Пишет GLM, утверждает человек. Вики и
  выгрузки целиком в промпт не кладутся.
- Личные термины остаются чертой персонажа: узел даёт вещам и местам свои имена поверх настоящих и
  защищает их.

**Последствия.** Бриф §2 («узел не знает игру») действует только в `masked`; §6 закрыт этим ADR.
Правило знаний в `prompt_template.md` зависит от режима. Perception остаётся критичной зоной.
**Откат.** `PERCEPTION_MODE=masked`.

## ADR-021. Цели сети — совет, цель узла выбирает узел (2026-10-16)

**Решение.**
- Контур сети в hive («Last Order») раз в N минут ведёт 1–3 **цели сети**: что сети не хватает
  (лестница прогресса, пробелы базы, частые причины смертей). Источник — правила плюс редкий вызов
  «умной» модели (ADR-023).
- Узел видит цели сети как знание, а не приказ. Личную цель он выбирает при рождении и пересматривает
  на рефлексии с поправкой на черты и завещания. Обычный шаг работает на личную цель.
- Насколько узел считается с целями сети, задаёт `trust_in_chat_and_nodes`.

**Последствия.** Бриф §1 «общей цели нет» сужается: общего мотора нет, общий совет есть.
Детали — docs/architecture/NETWORK.md (T-002).

## ADR-022. Общение узлов (2026-10-16)

**Решение.**
- Каналы: **Мисака-нет** через hive (мгновенно, на любом расстоянии, в игре не виден) и **игровой
  чат** (виден игрокам, с лимитом частоты).
- **Попутно, 0 вызовов.** Сообщение другому узлу — поле ответа обычного шага. Получатель видит его
  в наблюдении на следующем шаге. Так идёт координация: просьбы, предупреждения, «беру это на себя».
- **Болтовня** — отдельные короткие вызовы ради разговора. Жёсткий лимит на сеть
  (`CHATTER_CALLS_PER_HOUR`), очередь и выбор говорящего ведёт режиссёр реплик в hive. Он же гасит
  зеркальность: ограничивает число реплик в нити и даёт асимметрию через черты и разные знания.
- Сообщение другого узла — наблюдение, а не команда (как ADR-012 для чата).

**Последствия.** Бюджет вызовов: шаг, рефлексия, завещание, консолидация сети и болтовня в лимите.
Других вызовов без согласования нет.

## ADR-023. Уровни LLM; Jev локально на RTX 2070 (2026-10-16)

**Решение.**
- `node` — очень дешёвая облачная модель: шаг узла и болтовня.
- `smart` — дешёвая «умная» облачная модель (класс DeepSeek): рефлексия, завещание, консолидация и

**Альтернативы.** Локальная vLLM для узлов — отложена: облако дешевле времени на настройку.
**Откат.** Переменные уровня в `.env`.

## ADR-024. Транспорт сети — HTTP, без центральной шины (2026-10-16)

**Решение.**

**Откат.** Redis возвращается с появлением событий между процессами (стрим-режиссёр, Telegram).

## ADR-025. Чат во входе шага — наблюдение (уточнение ADR-012 для сети, 2026-10-16)

## ADR-026. Застревание: узел сам решает устраниться (2026-10-16)

**Решение.**

**Последствия.** Порог сторожа — порог предложения, а не смерти; задаётся в конфиге.
Решение пользователя 2026-10-16 (NETWORK.md §12, вопрос 2).

## ADR-027. Jev в C1 — облачный; FastJev на 2070 — запасной (уточнение ADR-004/023, 2026-10-16)

**Контекст.** Спайк T-005 (`docs/agents/jev.md`): целевой FastJev Qwen3.5-4B на RTX 2070 недостижим —
vLLM на Turing не стартует (`UVA is not available`), BF16 не входит в 8 ГБ, Q4_K_M через llama.cpp —
3–5 с на решение. В задержки C1 входит только Qwen3-0.6B: p95 144 мс на 8 вариантов, но качество
0.44 против 0.813 у целевой.

**Решение.**
- Основной `Decider` уровня `jev` — облачный Jev (TypeSafe через OpenRouter, ADR-004). Пользователь:
  стоит мало, использовать можно.
- Сервис `jev` (FastJev Qwen3-0.6B на 2070, профиль `jev`) остаётся локальным запасным путём и
  стендом A/B.
- `RuleDecider` — откат по таймауту и ошибке, как в ARCHITECTURE §3.

**Последствия.**
- Вызовы C1 уходят в облако и входят в бюджет. Цена (пользователь, 2026-10-17): $0.042 за 1M
  входа, выход бесплатно, задержка провайдера 148 мс. Jev зовётся по событию с полом 3 с на узел:
  ≈$0.06/ч на 3 узла (NETWORK.md §6), вся сеть ≈$0.24/ч.
- 148 мс — без сети до провайдера. p95 с этого хоста и таймаут C1 (сейчас 250 мс) — замер в T-015.
- В MVP C1 по-прежнему на правилах (NETWORK.md §2); Jev подключает T-015.

**Альтернативы.** Qwen3-0.6B локально как основной — быстро, но слабо. FastJev на 5070 Ti — карта
занята клиентом Minecraft. Только правила — остаётся откатом.
**Откат.** Бэкенд `Decider` в конфиге: облачный Jev, локальный FastJev или `RuleDecider`.

## ADR-028. Конвейер без оператора: headless-надзор и для критичных задач (уточнение ADR-019, 2026-10-17)

**Изменено ADR-040 (2026-10-25):** конвейер, субагенты и таблица effort сняты; действует то, что ADR-040 не отменил.

**Контекст.** Волна T-007, T-008, T-009 и T-020 прошла конвейер за 25 минут, но три критичные задачи
встали в `review` ждать оператора, а T-020 заблокировалась: у headless-надзора не было прав на docker.
Пользователь ведёт параллельно курс и ещё два проекта и не успевает передавать результаты между
харнессами. Курс — про вайбкодинг: время цикла важнее ручной проверки каждой задачи.

**Решение (пользователь, 2026-10-17).**
- Конвейер ZCode (`lo-run`) — основной путь. Он берёт все доступные задачи (`ready`, `changes`,
  `review`, `blocked` с вопросом) и идёт, пока они есть. После каждого слияния задачи из `queued`,
  у которых все `after:` уже `done`, сами переходят в `ready` (`merge_task.sh`).
- Headless-Claude проверяет и мержит любые задачи, критичные тоже. Модель — только Opus. Effort
  выбирает ZCode по задаче: `low`, `medium` или `high`; для критичной задачи — `high`, скрипт
  поднимает сам. `xhigh` и `max` не используются. Бюджет вызова — $2, $4 или $6.
- Headless-надзор решает сам: вердикты, включая `reject`, споры, вопросы исполнителя (режим `answer`),
  прямые правки по основаниям 1–3. Ему открыт стенд (`docker compose`), кроме `down`, `docker volume`
  и `docker system`.
- К оператору идёт только список «Эскалация оператору» из `coop-protocol.md`: выборы, которые
  CLAUDE.md оставляет пользователю, решения вразрез с ADR, секреты и удаление данных, исчерпанные
  лимиты, красный `main`.
- Скрипты протокола в `dev/` ведёт надзор как часть протокола, это не прямые правки.

**Последствия.**
- Код из критичных зон попадает в `main` без человека. Защита: effort `high`, построчная проверка
  и чек-лист без послаблений, лимит 3 headless-ревью на задачу. Сводка конвейера отдельно
  перечисляет влитое критичное, чтобы оператор мог проверить выборочно и пересмотреть новым раундом.
- Расходы на надзор растут с числом задач, лимиты на задачу их ограничивают. Сумма — в сводке.
- Одновременно не идут задачи с общими путями в «Можно трогать»; стенд — одна задача за раз.

**Откат.** Вернуть отказ для `criticality: critical` в `dev/call_supervisor.sh` и пункт про
критичные задачи в разделе «Конвейер» протокола.

## ADR-029. Потолок входа шага 4500 (2026-10-17)

**Контекст.** Честная сумма блоков шага KNOWLEDGE.md v2 §9 (3860) не влезала в потолок входа
2500 (NETWORK.md §6): шаблон личности — task1.md ч.2 §1 почти дословно, наследие 920, праймер
500, core 461. Варианты — резать блоки или поднять потолок — лежали в «Предлагаемых ADR»
KNOWLEDGE v2; рост расходов решает оператор. Решение оператора от 2026-10-17 передано через
диспетчера (ветка T-011, коммит `1a4b9c0`): поднять потолок до 4500 — из рекомендации надзора
~3900 оператор выбрал 4500 явно. T-011 заодно расширила шаблон (правило знаний в двух режимах
восприятия, правила шага, формат ответа StepReply), и `B_PERSONA` последовала за источником:
1000 → 1300.

**Решение.**
- Потолок входа шага — 4500 токенов, живёт в одном месте: `budget.STEP_INPUT_BUDGET`
  (NETWORK.md §6, строка «шаг»: 4500/200). Сумма блоков §9 — 4160 ≤ 4500, запас 340 — на
  заголовки блоков.
- `B_PERSONA` = 1300 привязана к рендеру шаблона с пустым наследием (обоих пресетов и обоих
  вариантов правила знаний); пин держит тест T-007. Выше 1300 не поднимать: шаблон сжимать.
- Блоки 1–4 (статичные для жизни узла) не режутся; вариант «резать» отклонён.

**Последствия.** Вход шага растёт на 2000 токенов против прежнего потолка: ≈ $0.22/ч на сеть
по ценам `node` без кеша (было ≈ $0.14/ч); блоки 1–6 статичны в рамках жизни — кеш префикса
держит их почти бесплатно. ADR-023 (бюджет почти нулевой) не меняется: новых вызовов LLM нет.

**Откат.** Вернуть `STEP_INPUT_BUDGET = 2500` и сжать блоки §9 до суммы ≤ 2500 (вариант (а)
«Предлагаемых ADR» KNOWLEDGE v2) — ценой потери завещаний и праймера в промпте.

**Контекст.** План курса из task1 (Telegram-чат и созвон, стрим с VTube Studio) писался до сети узлов.

## ADR-031. Умение = код: навыки сети на Python (2026-10-17)

**Контекст.** По лору «Мисака-нета» знание и умение сестёр — одно. Сейчас база хранит утверждения
(`danger|fact|recipe|term`), а набор действий узла фиксирован рычагами тела. NetTyan пробовал
`smolagents.CodeAgent` (`NetTyan/src/experiments/agent/smo_agent_experiments/mc_agent.py`): код на
каждом ходе — дорого, произвольное исполнение и обход правила «варианты строит код» (ADR-025).

**Решение (пользователь, 2026-10-17).**
- Навык — запись базы `kind: skill` с телом-функцией на Python и статусами знаний: `hypothesis` →
  `confirmed` (N удачных исполнений разными узлами) → `retired` (провалы).
- Пишет навыки **кузня** в hive: вызов `smart` по логам удачных цепочек рычагов и по заявкам рефлексии
  («это получилось трижды»), не чаще 4/ч на сеть. Новый вид вызова LLM — согласован этим ADR.
- Исполнение: только API тела (рычаги и геттеры `GameBody`), без импортов и встроенных функций вне
  белого списка, проверка AST до записи, таймаут и лимит шагов при исполнении, `@gamer` недоступен.
- Подтверждённый навык — ещё один вариант в списке шага. Узел выбирает только из вариантов кода;
  чат и сообщения узлов навык не вызывают и не пишут.
- Сновидец (занятие 6, опция): раз в сутки кодинговый агент дорабатывает навыки по логам; новая версия
  принимается после проверки на записанных состояниях.

**Последствия.** Реестр вызовов NETWORK.md §6 получает строку «кузня». Исполнитель навыков — критичная
зона. KNOWLEDGE.md слой 6 («навыки-процедуры») становится планом занятия 5.
**Откат.** Выключить кузню (`SKILL_FORGE=0`); навыки `confirmed` остаются вариантами или выключаются тем же флагом.

## ADR-032. Узел и сеть — агенты в сменном харнессе поверх aw (уточнение ADR-001, 2026-10-17)

**Контекст.** Курс советует делать персонажа самостоятельным агентом на рабочем месте `aw`. В старой
схеме поведение узла держал код: варианты шага, сборка промпта, таблица триггеров рефлексии, правила
целей и режиссёра. Пользователь 2026-10-17: поведение — в инструкциях и промптах, хардкода как можно
меньше; мы строим среду и харнесс, в которых сеть развивается сама; контуры разной скорости остаются.

**Решение (пользователь, 2026-10-17).**
- Узел — агент кодингового харнесса в своём контейнере `node-N`. Сеть — агент-персонаж Last Order
  (ADR-036). Рабочее место у обоих — персонаж `aw` (ADR-034).
- Харнесс сменный: OpenCode (модели через шлюз, ADR-033) или ZCode (GLM по подписке Z.ai). Выбор —
  по замеру расхода, цены и задержек на обоих (спайк). Рабочее место от харнесса не зависит.
- Контуры:
  - C0 — рефлексы uc, как раньше;
  - C1 — тонкий исполнитель в коде (`mind-N`): исполняет намерение агента, держит тело между ходами,
    ловит смерть и урон, будит агента (ADR-035). Тактику на угрозу выбирает Jev по текстовой политике,
    которую пишет сам агент;
  - C2–C4 (стратегия, общение, рефлексия) — один агент. Ритм выбирает он сам.
- Жизнь узла — гибрид: длинная сессия харнесса на жизнь для игры и общения; завещание — отдельная
  короткая сессия; рефлексию агент запускает сам (скил или подагент).
- Агент действует только через MCP-инструменты тела (`mind-N`) и hive, плюс bash внутри своего
  контейнера. Инструменты узкие и типизированные: нет `@gamer`, команд сервера и сырых команд uc.
- Код остаётся средой: тело и perception, база знаний hive, срок жизни, детектор смерти, аварийное
  завещание. Решатели уходят в инструкции: сборка промпта шага (`runtime/lastorder/step.py`), варианты
  по правилам, таблица триггеров, правила целей и режиссёра.

**Ответ на альтернативу ADR-001.** ADR-001 отверг «один агент с инструментами» из-за перегрузки
инструментами (nt, ~7k токенов). Здесь быстрое остаётся в C0 и C1, у агента немного узких
инструментов, а его ход измеряется секундами и минутами, не тиками. ADR-001 не отменяется: меняется
исполнитель медленных контуров.

**Последствия.**
- Схема шага C2 (наблюдение → ≤8 вариантов → `StepReply`) и ADR-029 (потолок входа шага) сняты.
  `runtime/lastorder/step.py` и `prompt_template.md` — источник для инструкций сестры, не рантайм.
- Задачи старой схемы T-014…T-019, T-021, T-023 не делаются; новая нарезка — NETWORK.md §11.
- Стоимость считается по сессиям, а не по вызовам (ADR-035).

**Альтернативы.** Старая схема (код строит варианты, LLM выбирает) — предсказуемо и дёшево, но
поведение зашито в код. Агент без C1 — тело простаивает между ходами и не успевает реагировать.
**Откат.** Задачи старой схемы вернуть из `rejected`; готовые модули среды общие для обеих схем.

## ADR-033. Песочница узла и доступ к LLM (2026-10-17)

**Решение (пользователь, 2026-10-17).**
- `node-N` — песочница: bash и файлы своего рабочего места, лимиты CPU и RAM. В сети ему видны только
  `mind-N` (MCP тела), `hive` (MCP сети), шлюз LLM и Z.ai. Py4j тела, RCON и интернет недоступны.
- Модели через OpenRouter — только через шлюз `llm-gateway` (LiteLLM proxy) вне контейнера узла.
  Ключи у шлюза; узел получает адрес и свой виртуальный ключ. Шлюз считает расход по узлу и режет по
  лимиту (ADR-035).
- Токен подписки Z.ai для харнесса ZCode лежит в `node-N` — осознанное исключение: при утечке теряется
  только квота. Если условия плана разрешают проводить GLM через шлюз, токен уходит в шлюз.
- Квота подписки общая с ZCode-воркером разработки (ADR-019). Расход узлов и разработки считается
  раздельно; у узлов свой потолок.
- Уровни ADR-023 становятся настройкой шлюза: модель харнесса узла, `smart` для Last Order
  и завещаний, `jev` для C1.

**Последствия.** `mind-N` остаётся в сетевом пространстве тела (ADR-015), `node-N` — отдельный сервис
со своей сетью. MCP поверх HTTP согласуется с ADR-024. Данные о ZCode без GUI в Linux и о лимите ×1.5
есть пока только в сторонних обзорах; проверяет спайк.
**Откат.** Ключ провайдера прямо в `node-N` (без учёта по узлу).

## ADR-034. Рабочее место сестры, ядро личности и самоправка (2026-10-17)

**Решение (пользователь, 2026-10-17).**
- Рабочее место — персонаж `aw` на узел: при рождении `agent/<serial>/` создаётся из шаблона сестры,
  после смерти уходит в архив (только чтение). Наследница начинает с чистого места и читает завещание,
  общую базу и цели сети.
- **Ядро** — база личности из task1 ч.2 §1 (общие черты, правило завещания, тон) и пресет имени
  (ADR-018). Только чтение, меняет оператор.
- Своё рабочее место сестра правит свободно: память, цели, привычки и заметки себе, скилы, подагенты,
  навыки-код, текстовая политика тактики для Jev.
- Общее (база знаний, общие навыки, общие инструкции сети) меняется **предложением**; решение
  принимает Last Order, пишет hive. Общие инструкции сети (не ядро) Last Order правит сам. Сновидец
  (правка кода харнесса) — позже.
- Навык-код (ADR-031) пишет сама сестра как скрипт рабочего места: он работает только через MCP тела
  (ADR-033). Общим навык становится через предложение. Кузня hive как отдельный вызов не нужна.
- Завещание пишет агент в сессии завещания. Если за таймаут его нет (сессия зависла, кончилась квота),
  раннер узла собирает аварийное завещание (`runtime/lastorder/will.py`). Смерти без завещания нет.
- Застревание (ADR-026): инструмент «устраниться» срабатывает только по сигналу сторожа C1, иначе
  отказ. Принудительная смерть по сроку 45 мин — за hive.

**Последствия.** Уточняет ADR-017 (hive — по-прежнему единственный писатель общей базы), ADR-018
(слот — постоянная тройка тело + `mind` + песочница), ADR-026 и ADR-031. Черты выпадают при рождении,
пишутся в `birth.json` и в рабочее место, числами в речь не выводятся.
**Откат.** Ядро расширяется до всего шаблона; самоправка — только память и цели.

## ADR-035. Ритм агента и потолок расходов (уточнение ADR-022, ADR-027, 2026-10-17)

**Решение (пользователь, 2026-10-17).**
- Ритм выбирает агент: инструмент `wait_events(timeout)` возвращает первое событие от C1 (урон, смерть,
  сообщение узла, чат, сигнал сторожа, завершение намерения) или истекает. Других толчков в сессию нет.
- Предохранитель в коде один — у шлюза: потолок ходов в минуту и денег в час на узел. При исчерпании
  шлюз отвечает ошибкой, C1 держит тело, узел «ждёт».
- Общение узлов — по инструкции, без режиссёра реплик и `CHATTER_CALLS_PER_HOUR` (ADR-022): болтовня
  — обычные ходы агента в общем потолке. Сообщения идут инструментами Мисака-нет и чата.
- Jev (ADR-027) зовёт C1 по событию угрозы; на вход — компактное состояние и политика агента
  (текстовый файл рабочего места, ограничен по длине).
- Ориентир бюджета — прежние ≤ $0.35/ч на 3 узла по деньгам плюс квота подписки; цифры даёт спайк.
  Правило CLAUDE.md «без согласования не добавлять вызовов» заменяется этим потолком.

**Последствия.** Предсказуемость расхода держит шлюз, а не форма цикла. Длинная сессия растёт —
компакция средствами харнесса; всё важное агент держит в файлах рабочего места (`aw`).
**Откат.** Фиксированный ритм: раннер будит агента раз в N секунд.

## ADR-036. Last Order — агент-администратор сети (уточнение ADR-021, ADR-030, 2026-10-17)

**Решение (пользователь, 2026-10-17).**
- Last Order — один агент на сеть, рабочее место `aw` в `hive`. Просыпается по событиям: смерть
  и завещание, пачка предложений, сообщение оператора, раз в N минут. Короткие сессии, память в файлах.
- Принимает и отклоняет предложения сестёр (знания, навыки, общие инструкции), ставит цели сети,
  пишет летопись (её публикует канал хроники ADR-030), отвечает сёстрам через Мисака-нет.
- Цели ставит сеть сама; оператор добавляет свои через `GOALS.md` Last Order. Для сестры цели сети —
  знание, не приказ (ADR-021 в силе).
- Писатель общей базы — по-прежнему hive: Last Order действует через его инструменты.

**Последствия.** Правила консолидации и целей (KNOWLEDGE.md, GOALS_COMMS.md) становятся его
инструкциями; контракт хранилища остаётся кодом.
**Откат.** Консолидация по правилам кода без агента.

## ADR-037. Чат и восприятие для агента (заменяет ADR-025 и режим `masked` ADR-020, 2026-10-17)

**Последствия.** Пункт критерия MVP «ни одного сырого id в `masked`» снят. `runtime/perception`

## ADR-038. Effort headless-надзора: `medium` по умолчанию, `high` — исключение (уточнение ADR-028, 2026-10-17)

**Изменено ADR-040 (2026-10-25):** конвейер, субагенты и таблица effort сняты; действует то, что ADR-040 не отменил.

**Решение (пользователь, 2026-10-17).**
- Headless-ревью работы субагентов конвейера идёт с effort `medium`, критичных задач тоже.
  `low` — как раньше, для мелкого некритичного.
- `high` — только исключения из таблицы `coop-protocol.md`:
  - одна и та же находка не закрыта два раунда подряд;
  - повторный `disputed` по уже отклонённой находке;
  - критичная задача с diff больше 800 строк;
  - явная просьба оператора.
  Причина пишется в «Вызовах надзора» и в сводке конвейера.
- `dev/call_supervisor.sh` для критичной задачи поднимает `low` до `medium`, но сам `high` не ставит.

**Последствия.** Пункт ADR-028 «критичной задаче — `high`» снят. Защита критичных зон теперь такая:
- построчная проверка и чек-лист без послаблений;
- самопроверка `lo-checker` до сдачи;
- лимит 3 headless-ревью на задачу;
- влитое критичное отдельной строкой в сводке, чтобы оператор проверил выборочно.

Расход на вызов по критичной задаче — $4 вместо $6.
**Откат.** Вернуть в `call_supervisor.sh` подъём критичной задачи до `high` и строку таблицы.

## ADR-039. Бюджет контекста конвейера ZCode (уточнение ADR-028, 2026-10-19)

**Изменено ADR-040 (2026-10-25):** конвейер, субагенты и таблица effort сняты; действует то, что ADR-040 не отменил.

**Контекст.** С 16 по 19 октября конвейер израсходовал около 640M входных токенов ZCode, около 70%
недельной квоты [проверено: `dev/zcode_usage.py`, экран квоты ZCode]. Из них 95% — кэш, то есть
одна и та же история сессии, отправленная заново. Средний контекст вызова был 106–168K, максимум — 513K.
Сжатие не срабатывало ни разу: у GLM-5.3 окно около 1M. Одна задача (T-024, ~800 вызовов) стоила
четверть всего расхода. Вывод (reasoning) — около 4% расхода, поэтому effort почти ничего не решает.

**Решение (пользователь, 2026-10-19).**
- Исполнитель после ~60 вызовов передаёт работу новому (итог `partial` с «Передачей»). Жёсткий
  предел — `maxTurns: 120`. Раунд доработки после `changes` делает новый исполнитель.
- Субагенты читают `docs/agents/worker-brief.md` вместо CLAUDE.md и протокола целиком; полные
  документы — по разделу. Правила CLAUDE.md при этом в силе.
- Проверки — `dev/check.sh` одним вызовом, ожидание стенда — `dev/wait_for.sh`. Опрос `sleep` в
  цикле запрещён.
- Диспетчер работает на GLM-5.3-Flash, без TodoWrite и опроса. Один чат — одна волна, до 8 закрытых
  задач. Посторонняя работа идёт в отдельном чате.
- `lo-worker-flash` (GLM-5.3-Flash, в 3 раза дешевле по весам квоты) берёт некритичные задачи
  только в `docs/`, `tests/`, `*.md`. Код, критичные зоны и стенд — у `lo-worker` на GLM-5.3.
- Большие волны идут в выходные (50% квоты) или в очереди простоя (`lo-run off-peak`,
  `OffPeakCreate`, без квоты плана).
- В ZCode выключены неиспользуемые плагины: jupyter-notebook, github, browser-use.

**Последствия.** Задача рассчитана на 1–2 эстафеты, до ~120 вызовов (`lo-plan`). Эстафета теряет
часть контекста, её компенсируют «Передача» и git. Расход по задачам и дням показывает
`dev/zcode_usage.py`. Если у Flash-задач растёт число раундов ревью, `lo-worker-flash` снимается.
**Откат.** Убрать эстафету и `lo-worker-flash`, вернуть чтение CLAUDE.md целиком.

## ADR-040. Два агента без субагентов: ZCode делает задачи по очереди в одном чате (заменяет конвейер ADR-028, ADR-038, ADR-039, 2026-10-25)

**Контекст.** Решение пользователя (2026-10-25): конвейер `lo-run` с диспетчером и субагентами
`lo-worker`, `lo-worker-flash`, `lo-checker` и `lo-scout` не устраивает. Процесс сводится к двум
агентам, Claude и ZCode, без субагентов, а протокол упрощается.

**Решение.**
- ZCode работает в одном чате без субагентов (скил `lo-work`):
  - берёт задачи по очереди, следующую печатает `dev/tasks.sh --next`;
  - после сдачи сам вызывает headless-Claude;
  - по `changes` дорабатывает в том же чате.

  Чат ZCode — один за раз, поэтому правила о пересечении «Можно трогать» и очереди стенда сняты.
- Предел чата — 3 закрытые задачи или ~150 вызовов инструментов. Незаконченную задачу закрывает
  раздел «Передача» в `report.md`. Довод ADR-039 о квадратичном расходе контекста в силе.
  [предположение: числа подобраны по данным ADR-039, пересмотреть по `dev/zcode_usage.py`]
- Сняты:
  - субагенты `.zcode/agents/`, скил `lo-run`, очередь off-peak, `docs/agents/worker-brief.md`;
  - самопроверка `lo-checker` и дешёвый исполнитель `lo-worker-flash`;
  - проверка плана (режим `plan`);
  - таблица effort и автоопределение критичности в `call_supervisor.sh`;
  - статус `queued`: зависимость задаётся полем `after:` у задачи `ready`;
  - раздел «Вызовы надзора» в `report.md`.
- Скилы ZCode `lo-take`, `lo-submit`, `lo-blocked`, `lo-call-supervisor` и `lo-run` слиты в `lo-work`.
- Headless-надзор — только Opus, effort `medium`, $4; `high` ($6) — только по просьбе оператора.
  Лимит — 3 `result` и 2 `answer` на задачу. Полномочия и эскалация — как в ADR-028.
- `criticality: critical` ставит Claude в `lo-plan`. На ревью критичной считается и задача, чей
  diff задевает критичную зону. Построчная проверка и основание 1 прямой правки сохраняются.

**Последствия.**
- Задачи не идут параллельно: порция дольше, зато нет конфликтов слияния и очереди стенда.
- Критичный код защищают построчное ревью Opus и чек-лист; самопроверки до сдачи нет.
- Контекст ZCode растёт внутри чата. Доработка в том же чате дешевле перечитывания с нуля, но
  предел чата обязателен.

**Откат.** Вернуть файлы из `b86b1f7` (`git checkout b86b1f7 -- <путь>`): `.zcode/agents/`,
`.zcode/skills/`, `docs/agents/worker-brief.md`, `docs/agents/coop-protocol.md`, скилы
`.claude/skills/lo-*`, скрипты `dev/` протокола.

## ADR-041. Интерактивная сеть: харнесс Pi, консоль оператора, долгая сессия Last Order, мастерская и гранты (уточняет ADR-012, ADR-031–037; снимает Telegram-часть ADR-030, 2026-10-26)

**Контекст.** После T-039 стенд живёт (3 слота, 2 ч), но с ним нельзя взаимодействовать: оператор
дописывает `INBOX.md` через `docker exec`, Last Order отвечать не может, сёстры и Last Order живут
в одноразовых сессиях (Hermes, OpenCode), в которые ничего не вставить на ходу. Решение
пользователя (2026-10-25/26): общаться с Last Order, сёстрами и сетью как с кодинговым агентом,
в одном интерфейсе, а инструменты сети пусть строит сама сеть.

**Решение.**
- **Харнесс — Pi** (pi.dev) для Last Order и сестёр. Основной провайдер — Z.ai Coding Plan
  (`models.json`, `openai-completions`); запасной — OpenCode через шлюз, переход — с тревогой
  оператору в консоль. Hermes остаётся в образе резервом. Доводы: штатные `steer` (после ближайшего
  вызова инструмента) и `follow_up` (когда агент свободен), расширения, которые агент пишет сам.
  [источник: pi.dev, docs/rpc.md, docs/extensions.md; на стенде не проверено — T-041]
- **Консоль оператора** — одна веб-страница со всеми агентами: Last Order, живые сёстры, канал
  «сеть» (всем сразу), мёртвые — только чтение. Берётся готовое решение (кандидаты: HAPI, pi-web),
  выбор — по прогону T-041. Своя консоль — только если ни одно не подходит.
- **Два режима ввода.** *Голос извне* — сообщение, которое сестра слышит как внешнее и взвешивает
  по своим чертам (наблюдение, как ADR-012/037). *Мысль* — вставка в её контекст как её
  собственной мысли, без пометки для неё; в логах и консоли помечена как мысль оператора.
- **Оператор — участник Мисака-нет.** Сестра и Last Order могут писать оператору первыми, по
  своему усмотрению; на жизнь — потолок сообщений.
- **Last Order — одна долгая сессия**: события сети (смерти, предложения, таймер) приходят
  сообщениями в ту же сессию, сообщения оператора — между ними; Pi сжимает контекст, память в
  файлах остаётся. Короткие сессии по событию (ADR-036) сняты.
- **Мастерская.** Инструменты-возможности Last Order и сестёр (Telegram, что угодно ещё) код
  проекта не пишет. Last Order пишет расширения Pi в своей `workshop/`, подключает их себе и
  публикует сёстрам через hive (писатель базы — по-прежнему hive, ADR-017). Сестра пишет свои в
  своём рабочем месте и предлагает в общее через Last Order (ADR-031, ADR-034).
- **Гранты.** Новые возможности наружу — по запросу и одобрению: агент или оператор запрашивает
  egress на домен или секрет, оператор одобряет в консоли, секрет лежит в хранилище hive и
  доходит только до процесса инструмента, которому выдан; egress — через прокси со списком
  разрешённого. Отзываемо. Всё прочее в ADR-033 в силе.
- **Telegram** — не задача кода. Если оператор захочет канал, Last Order строит его сама через
  мастерскую и гранты. Telegram-часть ADR-030 снята; голос и стрим ADR-030 — в силе.
- Мир остаётся жёстким: защиты первых минут жизни нет (T-039: смерти через 12–14 с — дело сети).

**Последствия.** Задачи T-040…T-047. Код по-прежнему — среда (ADR-032): харнесс, консоль, связь
консоли с hive, мастерская и механизм грантов; поведение — в инструкциях. Новый расход: долгая
сессия Last Order и её работа в мастерской идут на квоте Z.ai Coding Plan, общей с ZCode и
узлами; деньги — только при отказе на OpenCode, в потолке шлюза.
**Откат.** `NODE_HARNESS=hermes`, Last Order — `ADMIN_HARNESS=opencode` с короткими сессиями;
консоль и гранты не поднимать.

## ADR-042. Консоль — HAPI, «мысль» снята, доска задач в hive (уточняет ADR-041, ADR-033, 2026-10-26)

**Контекст.** T-041 (`docs/agents/console-choice.md`): ни одна готовая консоль не цепляется к
сессии Pi, которую запустил наш раннер, — каждая сама запускает pi. «Мысль» как реплика самого
агента расширением Pi 1.4.0 не вставляется: `sendMessage` и `before_agent_start` дают
`role: custom` [проверено: T-041 session5/6]. Решение пользователя (2026-10-26): консоль — HAPI,
потому что через неё проще подключать новых персонажей и харнессы; «мысль» не нужна, хватит
чата; сказать узлу или сети «сделай» — через доску задач, на ней же агенты оставляют запросы
разрешений.

**Решение.**
- **Консоль — HAPI** (`github.com/tiann/hapi`, AGPL-3.0, без правок, версия пинится). Хаб —
  отдельный сервис на стенде, без relay, порт только на `127.0.0.1`. Агента запускает CLI HAPI:
  раннер `node-N` и admin Last Order запускают `hapi pi`, а не `pi --mode rpc`. HAPI сам держит
  RPC Pi и передаёт ввод оператора [источник: hapi docs/guide/how-it-works.md, agents.md;
  на стенде не проверено — T-044]. Новые харнессы (`hapi opencode` и др.) — выбор агента в HAPI.
- **Ввод оператора — только чат.** Сообщение из HAPI — голос оператора: наблюдение (ADR-012,
  ADR-037), агент видит, что это оператор. Режим «мысль» снят, вставки в контекст нет.
- **Доска задач в hive.** Записи: задача, запрос, сообщение, тревога; адресат — узел, Last
  Order, `net`, оператор. Пишут: оператор (страница hive), Last Order (задачи сёстрам и сети),
  сёстры (запросы разрешений и помощи оператору или Last Order, задачи сёстрам). Агенты читают и
  пишут через MCP hive; новая запись — повод проснуться.
- **Вес задачи оператора — сильная просьба.** По инструкции это высший приоритет сети; сестра
  может отказаться, но отвечает на доске с причиной. Задачи Last Order и сестёр — совет, как цели
  сети. Правило — в инструкциях, не в коде (ADR-032).
- **Страница доски** — маленькая страница hive под паролем, на `127.0.0.1`: список, новая
  задача, одобрить или отклонить запрос. Тревоги среды (переход на запасной харнесс) и сообщения
  агентов оператору — там же. Одобрение грантов (ADR-041) — кнопкой на этой странице.
- **ADR-033:** у `node-N` новый внутренний выход — хаб HAPI. В песочнице лежит токен CLI HAPI.
  Что этот токен позволяет сестре через bash (чужие сессии, запуск), проверяет T-044. Если даёт
  больше своей сессии — решение оператора.

**Последствия.** Спецификация доски — `docs/architecture/TASKBOARD.md`. T-042 становится задачей
о доске, страница — T-049, доставку в сессию берёт T-048 (`misaka-link` без «мысли»), T-044 — спайк HAPI, T-043 и T-045 запускают Pi через HAPI, T-046 одобряет гранты на
доске. Новых видов расхода LLM нет. **Откат.** Агентов запускать без HAPI (`pi --mode rpc` или
прежние харнессы), доска работает без консоли.

## ADR-043. Команды сервера сестре — команды игрока, запрет списком (уточняет ADR-037, ADR-013, 2026-10-31)

**Контекст.** Прогон T-052: задача оператора «/warp pers» повисла — `say` отвергает `/` (ADR-037),
сестра верно не смогла её выполнить. На внешнем сервере (mc.example.net) без `/login` тело не
играет; регистрацию в сессии T-052 делали вручную из среды.

**Решение (оператор, 2026-10-31).** Первая редакция того же дня (список разрешённого) заменена
по решению оператора на запрет списком.
- Сестре доступны те же команды, что обычному игроку сервера: `/tpa`, `/sethome`, `/warp` и
  подобные. Прав администратора у аккаунтов `LastOrder01..03` нет, права проверяет сам сервер
  [проверено: у `mc-server` нет `OPS`, `docker/compose.yml:126-143`].
- В MCP тела — инструмент `server_command(command)`. Ограничение — список запрещённых команд в
  конфиге стенда (общий и на слот). По умолчанию в нём команды входа и пароля: `/login`, `/l`,
  `/register`, `/reg`, `/changepassword`, `/unregister`. Список ведёт оператор; рабочее место
  сестры и Last Order его не меняют.
- Ответ сервера приходит обычными `chat.line` через фильтр восприятия, отдельного канала нет.
- `say` по-прежнему без `/` и `@`.
- Вход на сервер (`/login`, `/register`) делает среда (`mind-N`) при входе в мир. Пароль — секрет
  стенда в `.env`, агенту не виден, в логах маскируется.

**Альтернативы.** Список разрешённого — отклонён оператором: команды обычного игрока безопасны
по правам сервера, список разрешённого только мешает. Снять запрет `/` в `say` — отклонено:
команда и реплика смешиваются в логах и в восприятии. Разрешать `/` только при открытой задаче
оператора — отклонено: условие обходится, правило про ситуацию в коде (ADR-032).

**Последствия.** «Нет команд сервера» в ADR-037 читается как «нет команд из запретного списка и
команд администратора». Если аккаунту узла выдадут права администратора, этот ADR надо
пересмотреть. Задача — T-053.
**Откат.** Запрет `/` целиком в списке стенда: инструмент есть, но ничего не пропускает.

## ADR-044. Last Order управляет составом сети без одобрения на каждое действие (уточняет ADR-033, ADR-041, 2026-10-31)

**Контекст.** Оператор хочет, чтобы Last Order сама поднимала и снимала сестёр, переводила слоты
на другие серверы и перезапускала сервер, без жёстких ограничений. В сессии T-052 это делали руками.

**Решение (оператор, 2026-10-31).**
- Last Order пишет на доску запрос `infra`, исполнитель на хосте выполняет его сразу. Одобрения
  оператора на каждое действие нет. Оператор видит каждое действие и итог на доске и может
  выключить исполнитель одним переключателем.
- Безопасность своих действий Last Order оценивает сама по инструкции. Второе мнение — локальный
  классификатор (GLiNER2.5-multi-Decide, запасной — Laya) в процессе исполнителя на хосте, на GPU
  оператора, без спайка, сразу с тестами на модели. На `dangerous` исполнитель держит запрос до
  решения оператора (T-060).
- Набор действий исполнителя закрыт, но широк: поднять, снять или перезапустить слот; перевести
  слот на сервер; перезапустить `mc-server`; состояние стенда и хвост логов. Произвольный shell и
  произвольные команды Docker не исполняются: доступ к Docker хоста равен правам администратора
  хоста (решение надзора).
- Сокета Docker нет ни в одной песочнице (ADR-033 без изменений). Гранты на выход наружу и
  секреты (ADR-041) — по-прежнему с одобрения оператора.

**Альтернативы.** Одобрение каждого действия (образец грантов T-046) — отклонено оператором:
мешает Last Order управлять сетью. Сокет Docker в контейнере Last Order — отклонено: права
администратора хоста у агента.

**Последствия.** Задачи T-057 (исполнитель), T-060 (классификатор).
**Откат.** Выключить исполнитель: запросы `infra` остаются на доске без исполнения.

## ADR-045. Видео сети строит Last Order; среда даёт только картинку и запись (заменяет стрим-часть ADR-030, 2026-10-31)

**Контекст.** Оператор хочет агентов, которые держат фокус на самой интересной сестре, пишут материал
и собирают ролик, а возможно, дают сёстрам инструмент «снимать или нет». ADR-030 закладывал
режиссёра на правилах в коде и тело-камеру в режиме наблюдателя. Наблюдателя нет на чужих серверах,
а сёстры будут играть и там. Конспект и набор инструментов — docs/agents/video-toolkit.md.

**Решение (оператор, 2026-10-31).**
- Режиссёра, монтажёра, оценку интереса, отметки сестёр и эфир код не пишет. Нужны ли они и какими
  они будут, решает и программирует Last Order в мастерской (ADR-041), с публикацией сёстрам
  через hive. Остаётся ли монтажёр её ролью или отдельным агентом, тоже решает она.
- Начать с простого: рендер тел на CPU в Docker (`BODY_RENDER=xvfb`, уже есть), без GPU и Windows-клиентов.
- `mc-server` переходит на Fabric, версии загрузчика и модов закреплены (T-062). Клиентские моды
  (Flashback и т. п.) ставятся в тела и работают на любом сервере; серверные — только на своём.

**Среда (предложение надзора, оператор поставил задачи 2026-10-31).**
- **Камера тела.** Тело с рендером отдаёт свой экран потоком: ffmpeg `x11grab` с дисплея Xvfb → RTSP.
  Дистанция прорисовки и память тела для съёмки — в конфиге слота (сейчас 2 чанка и 768M).
- **Сервис `media`** — готовый MediaMTX: принимает потоки тел и пишет их в кольцевой буфер
  (`record`, `recordDeleteAfter` — страховка диска, по умолчанию 1 сутки). По HTTP отдаёт список
  записей и вырезку по времени (`/list`, `/get?start=&duration=`). Доступ — из контейнера
  `last-order` по внутренней сети. Сёстрам — только через инструменты, которые опубликует Last Order.
- В образе `last-order` есть ffmpeg. Журналы сети (hive `events.jsonl`, `log.jsonl` слотов) Last Order
  читает только на чтение [проверить: смонтированы ли журналы слотов].
- OBS на хосте, ключ стрим-платформы, внешние API (распознавание, TTS, генерация) — по грантам
  (ADR-041).

**Альтернативы.** Режиссёр на правилах в hive (ADR-030) отклонён: это поведение в коде. Отдельный
наблюдатель-камера не работает на чужих серверах. Повторы Flashback рендерятся только в GUI, поэтому
остаются ручной страховкой. Серверные ServerReplay и Flashback Server работают только на своём сервере.

**Последствия.** Стрим-часть ADR-030 (режиссёр на правилах, тело-камера) снята; голос ADR-030 в силе.
Задачи T-062 (Fabric), T-063 (камера и `media`), T-064 (доступ Last Order),
T-065 (прогон: CPU, память, C1). Видео-задача Last Order — текстом на доске после T-047 и T-064
(docs/agents/video-toolkit.md §10).
**Откат.** Камеру выключает флаг слота; `media` — отдельный сервис, его можно не поднимать.

## ADR-046. Очереди ZCode параллельно, блокировка стенда, мелкие находки чинит надзор (уточняет ADR-040, 2026-11-07)

**Контекст.** Оператор (2026-11-07): задачи идут 2–3 ч, нужно быстрее. По git-истории T-043…T-055
[проверено: git log]: работа до сдачи — 36 мин … 1 ч 30 мин, каждый раунд `changes` — ещё 25–35 мин,
простой между задачами и чатами — от 50 мин до ночи. Цепочка Fabric и камер (T-062 → T-065) стояла
за не связанной с ней T-055, потому что чат ZCode — один.

**Решение** (одобрено оператором 2026-11-07).
- Поле `lane:` у задачи, по умолчанию `a`. На очередь — свой чат ZCode, очереди идут параллельно.
  `dev/tasks.sh --next --lane L` выдаёт только свою очередь. Цепочка `after:` — в одной очереди.
- Стенд один (compose `lastorder`): `dev/stand.sh lock|unlock T-NNN` перед действиями, которые
  поднимают или меняют сервисы, и после. Блокировка старше 2 ч считается брошенной.
- Основание прямой правки 5 «мелочь на ревью»: очевидная правка до ~20 строк без выбора решения
  надзор делает сам в worktree задачи и выносит `accept`, а не `changes`.
- Основание 6 «задача надзора»: задачу на код с `owner: supervisor` надзор делает по решению
  оператора, код идёт в DIRECT_EDITS. Первая — T-056.

**Последствия.**
- Две очереди тратят квоту Z.ai вдвое быстрее; когда работают сёстры на стенде, квоту делят три
  потребителя. При упоре в квоту второй чат не запускать.
- Слияния двух очередей могут конфликтовать в общих файлах (`docker/compose.yml`): конфликт ловит
  `merge_task.sh`, разрешает вливающий вторым.
- Стенд поднимается из worktree той задачи, у которой блокировка; между прогонами разных очередей
  сервисы пересоздаются по чужому compose. Мир не сбрасывается.
- Прямых правок станет больше; каждая записана в DIRECT_EDITS.

**Откат.** Убрать `lane:` из задач (все станут `a`), не запускать второй чат; основания 5–6 удалить
из протокола и `lo-direct-edit`.

## ADR-047. Протокол двух агентов снят: Claude Code пишет код сам на `main` (заменяет ADR-019, ADR-040, ADR-046, 2026-11-10)

**Контекст.** Оператор (2026-11-10): протокол (задача → ZCode → ревью → merge) тормозит, видимого
прогресса нет 3–4 недели.

**Решение.** Claude Code делает задачи сам, прямо в `main`, без worktree, раундов ревью,
DIRECT_EDITS и headless-вызовов. Файлы задач в `docs/agents/work/` остаются заметками: что
сделано и как проверено — короткой записью в `report.md`, статус — `done`. Остальные правила
(среда, а не поведение; секреты; Docker; `unionclef/` и `NetTyan/` — только чтение; пометки
проверено/предположение) в силе.

**Откат.** Вернуть раздел «Два агента» в CLAUDE.md и скрипты `dev/merge_task.sh` и т. п.

## ADR-048. Запретные темы чата других игроков не доходят ни до одной модели (уточняет ADR-012, ADR-037, 2026-11-11)

**Контекст.** Оператор (2026-11-11): провайдер может забанить аккаунт за то, что ему прислали,
даже если сестра ничего не повторит в чате. Строку на откровенную тему пишет чужой игрок —
выбора у сети нет, она должна её не увидеть.

**Решение.**
- Фильтр стоит в `mind-N`, в единственной двери текста чужих игроков: `Executor.chat_entry`
  (события `chat.line` и `observe()`), имена говорящих и сущностей, текст смерти и урона.
  Строка на запретной теме отбрасывается целиком до события, журнала и `observe()`; имя
  заменяется видом сущности. Сёстры, Last Order (она читает журналы `mind-N`), завещания и
  `jev` её не получают.
- Список тем — данные оператора: `docker/mind/chat-topics/topics.txt`, только чтение, только в
  `mind-N` (`CHAT_TOPICS_PATH`). В песочницы и к Last Order список не монтируется: сам список —
  тоже текст для провайдера. Правка применяется без перезапуска (~5 с); сломанная правка оставляет
  прежний список, при старте — ошибка, а не открытый фильтр.
- В журнал пишется только имя темы и место (`chat.filtered`, `topic`, `scope`), текст — никогда.
- Сопоставление по основам, с приведением похожих букв, цифр, повторов и букв через точки
  (`runtime/perception/topics.py`). Моделей нет: детерминированно, на CPU.

**Альтернативы.** Фильтр в шлюзе — не покрывает подписку Z.ai у харнесса сестры (ADR-033,
исключение). Локальный классификатор — модели T-060 не дали точности и на более простой задаче.

**Не покрыто.** Картинка камеры (ADR-045) показывает чат на экране, если кадр уйдёт в модель
с картинками. Текст табличек и книг инструментами сейчас не читается.

**Откат.** `CHAT_TOPICS_PATH=` в `.env` выключает фильтр (mind пишет предупреждение).

## ADR-049. Второе мнение о запросах infra снято (уточняет ADR-044, 2026-11-11)

**Контекст.** T-060: ни одна локальная модель (GLiNER2, Laya, Qwen3-0.6B) не дошла до 0.8 на
наборе из 48 запросов (лучшая — 0.48, опасные помечались безопасными).

**Решение (оператор, 2026-11-11).** Исполнитель infra работает без второго мнения. Защита —
закрытый набор из 7 действий с проверкой аргументов, ни shell, ни Docker; по одному запросу;
каждое действие и итог на доске; выключатель оператора. Свою безопасность Last Order оценивает
по инструкции. Каркас классификатора (`dev/safety/`, `tests/safety_cases.yaml`) остаётся для
возврата к вопросу.

**Остаточный риск.** `slot_server` отправляет аккаунт слота на любой адрес (внешний сервер —
бан аккаунта, адрес стенда); `logs` отдаёт хвост любого сервиса в контекст Last Order; частые
`slot_restart` и `mc_restart` обрывают жизни сестёр. Всё видно на доске.

**Откат.** Вернуть T-060 с моделью на GPU или дообучением.

## ADR-050. Ядро стенда стартует само, слоты поднимает Last Order, тело — забота разума (уточняет ADR-044, NETWORK §9, 2026-11-11)

**Контекст.** Оператор (2026-11-11): один `up.sh` поднимал всё — три тела, три разума, трёх сестёр,
мир и ядро, а политики `on-failure` не воскрешали стенд после перезапуска Docker. Исполнитель infra
был скриптом на хосте: после перезагрузки поднять слот было некому. Оператор хочет, чтобы сами
стартовали только нужные сервисы, слоты поднимала Last Order (или оператор с доски), а тело
поднимал и менял разум — сети нужно уметь играть в другие игры.

**Решение (оператор, 2026-11-11).**
- Ярусы compose. Ядро без профиля, `restart: unless-stopped`: `hive`, `last-order`, `hapi-hub`,
  `llm-gateway`, `gateway-db`, `zai-egress`, `egress`, `media`, `infra`. Слот (`profiles: [slots]`) —
  `node-N` и `mind-N`; тело (`[bodies]`) — `body-N`; мир (`[world]`) — `mc-server`. У слотов, тел
  и мира `restart: "no"`: их поднимает только запрос на доске. `up.sh` без аргументов поднимает
  ядро и создаёт остальное остановленным, с ключами.
- Разум и тело — соседи, а не одно сетевое пространство. Частная сеть `link-N` (internal, только
  `body-N` и `mind-N`, разум на фиксированном 10.250.N.3). В теле socat: `:25433` → py4j uc на
  localhost (`range=` только адрес разума) и обратный вызов `127.0.0.1:25334` → `mind-N:25334`.
  uc не меняется. `node-N` в `link-N` не входит — сырого моста в песочнице нет (ADR-033).
  MCP тела слушает `mind-N:8700`.
- Тело — забота разума (`runtime/mind/bodyctl.py`). Тело не ответило за 20 с после старта —
  разум просит `body_up {slot, kind}`; ответившее тело молчит 90 с — `body_restart`; после просьбы
  ждёт загрузку (420 с). Вид тела (`BODY_KIND`, сейчас `minecraft`) выбирает адаптер `GameBody`:
  другая игра — новый адаптер и сервис тела, слоты не меняются.
- Права на доске. Раннер слота (ключ раннера есть и у разума) пишет `body_up`, `body_down`,
  `body_restart`, `slot_restart` только про свой слот, через `POST /board/infra/slot`, автор
  `runner:LastOrder0N`; не больше 3 перезапусков за 10 мин, дальше 429 и тревога `stuck`. Оператор
  пишет любые infra-запросы (кнопки слотов на странице доски). Раннер, у которого разум молчит
  90 с, просит `slot_restart` раз в 300 с.
- Исполнитель infra — контейнер ядра (заменяет «исполнитель на хосте» из ADR-044). Образ
  `docker:29.9.2-cli` + compose v5.6.1 (sha256 сверяется), сокет Docker, репозиторий только на
  чтение по пути, который видит демон (`STAND_DAEMON_ROOT`, на Docker Desktop
  `/run/desktop/mnt/host/c/...`), `.stand/` на запись (переезды слотов). `read_only`, `cap_drop: ALL`,
  `no-new-privileges`, 256 МБ, сеть `infra-net` (internal, только с hive), здоровье — по пульсу
  цикла опроса. Набор действий закрыт как прежде, плюс `body_up/body_down/body_restart`;
  shell и произвольного Docker нет.
- Мир по требованию: исполнитель поднимает `mc-server` перед телом, которое играет дома, и
  останавливает его, когда не осталось ни одного тела.
- После старта процесса desk Last Order получает пробуждение `start` («слоты могут быть сняты»)
  и сама решает, какие слоты поднять.
- Логи всех сервисов — json-file, 10 МБ × 3.

**Альтернативы.** Исполнитель на хосте (ADR-044) — после перезагрузки его некому запустить.
Сокет в `last-order` — права администратора хоста у агента (отклонено в ADR-044). Тело как
зависимость compose у разума — разум не может сменить тело на тело другой игры.

**Остаточный риск.** Контейнер `infra` — администратор хоста через сокет и держит ключи всего
стенда (`.env` на чтение). Агента в нём нет, он только опрашивает доску своим ключом. Сокета нет
ни в одной песочнице и в `last-order`.

**Не проверено.** Автостарт ядра после перезагрузки хоста: держится на `unless-stopped` и
«Start Docker Desktop on login»; оператор смотрит при ближайшей естественной перезагрузке.

**Откат.** `git revert` коммитов ADR-050; старый `up.sh` поднимал всё сразу.
