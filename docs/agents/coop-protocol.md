# Протокол двух агентов: ZCode исполняет, Claude проверяет

Решения — ADR-019 и ADR-040. Этот документ — канон. Скилы ссылаются сюда и правила не пересказывают.

## Роли
| Роль | Харнесс | Делает | Не делает |
|---|---|---|---|
| worker | ZCode (Z.ai, GLM) | пишет код и тесты по задаче, сдаёт отчёт, вызывает надзор | не коммитит в `main`, не меняет статусы надзора, не ставит себе задачи |
| supervisor | Claude Code | нарезает задачи, проверяет, мержит, ведёт BOARD | не правит код сам, кроме случаев из раздела «Прямые правки» |
| оператор | человек | запускает ZCode, разбирает эскалации, решает споры | — |

Задачи, которые надзор делает сам (документы, ролики — не код проекта), помечаются `owner: supervisor`
во frontmatter: `dev/tasks.sh --next` их пропускает. Ветка — `c/T-NNN-<slug>`, merge — тем же
`dev/merge_task.sh`.

Субагентов нет ни у одного агента. Оба подчиняются [CLAUDE.md](../../CLAUDE.md) целиком. ZCode его
сам не загружает, поэтому [AGENTS.md](../../AGENTS.md) требует прочитать его перед работой.

## Цикл
1. Claude ставит задачи (`lo-plan`), статус `ready`, порядок — поле `after:`.
2. Оператор пишет ZCode «возьми задачи» (скил `lo-work`). ZCode в одном чате делает задачи по
   очереди:
   - берёт следующую (`dev/tasks.sh --next`);
   - пишет код и сдаёт;
   - вызывает headless-Claude на ревью;
   - по `changes` дорабатывает в том же чате;
   - после `accept` берёт следующую.
3. Чат заканчивается после 3 закрытых задач (влиты или ждут оператора) или ~150 вызовов
   инструментов. Затем ZCode пишет сводку оператору, следующая порция идёт в новом чате (ADR-039).

Чат ZCode — один за раз. Поэтому задачи не пересекаются по файлам и не делят стенд.
Оператор может в любой момент проверить задачу сам: пишет Claude «проверь T-NNN». Headless-вердикт
он пересматривает новым раундом.

Результат, которого нет в файлах задачи или в git, не считается сделанным.

## Вызов надзора
`bash <корень>/dev/call_supervisor.sh result|answer T-NNN [high]` из worktree задачи. Скрипт
берётся из корня: копия в ветке может быть старше `main`. Правила и скрипты headless-Claude тоже
читает и запускает из корня.
- Режимы:
  - `result` — ревью при статусе `review`, при `accept` с merge;
  - `answer` — ответ на вопрос исполнителя при статусе `blocked`.
- Модель — только Opus, effort `medium`, бюджет $4. `high` ($6) — только если попросил оператор.
  `SUPERVISOR_BUDGET_USD` переопределяет бюджет.
- Права: `dontAsk`. Разрешены:
  - чтение и правка файлов;
  - `git`, кроме push, reset, clean и rebase;
  - `uv run`, `python tools/*`, скрипты `dev/`;
  - стенд: `docker compose`, кроме `down`, а также `docker ps` и `docker logs`.

  `docker volume` и `docker system` запрещены.
- Лимит на задачу — 3 `result` и 2 `answer`, дальше задача ждёт оператора. Оператор может дать ещё
  (`SUPERVISOR_MAX_ROUNDS`).
- Скрипт отказывает:
  - при грязном дереве, чужой ветке или запуске из корня;
  - при `answer` на задачу, которая уже ждёт оператора (`Blocked: нужен оператор`);
  - сверх лимита.
- Headless-Claude решает сам всё, чего нет в «Эскалации оператору»:
  - вердикты `accept`, `changes`, `reject` (при `reject` переписывает `task.md`, статус `ready`);
  - споры `disputed`;
  - ответы на вопросы, включая уточнение или расширение «Можно трогать»;
  - прямые правки по основаниям 1–3.
- Раунды надзора в `review.md` помечены `· headless`, по ним скрипт считает лимит. Стоимость
  каждого вызова ZCode пишет в сводку чата.

### Эскалация оператору
К оператору идёт только это. Тогда headless-Claude ставит `status: blocked` и строку
`Blocked: нужен оператор — <причина>`, вердикт `blocked`:
1. Выбор, который CLAUDE.md оставляет пользователю: пресет имени, 4-я общая черта, новый вызов
   LLM или рост расходов сверх списка вызовов, правка `descriptions.yml`.
2. Решение вразрез с ADR или CLAUDE.md, которое не обойти внутри задачи: нужен новый ADR.
3. Секреты и `.env*`, удаление данных мира или базы сети, push, действия вне репозитория.
4. Исчерпан лимит вызовов или скрипт надзора упал.
5. `main` красный, и прямая правка его не чинит.

Всё остальное, включая критичные зоны, решают агенты.

## Файлы
```
docs/agents/work/
  BOARD.md              таблица задач
  DIRECT_EDITS.md       журнал прямых правок Claude (только дописывать)
  _templates/           task.md, report.md, review.md
  T-NNN-<slug>/
    task.md             пишет Claude; ZCode меняет только status и строку Blocked
    report.md           пишет ZCode, раунды дописываются
    review.md           пишет Claude, раунды дописываются
```
- Номер `T-NNN` — сквозной, трёхзначный, следующий после максимального в BOARD.
- `slug` — 2–4 английских слова через дефис.
- Раунды не переписываются: новый раунд — новый раздел `## Раунд N` в конце файла.
  Раунд N отчёта отвечает на раунд N−1 ревью.

## Статусы
| Переход | Кто |
|---|---|
| `draft → ready` | Claude, только если критерии приёмки проверяемы |
| `ready → in_progress`, `changes → in_progress` | ZCode |
| `in_progress → review` | ZCode |
| `review → changes` / `accepted` / `ready` (reject) | Claude |
| `accepted → done` | Claude после merge |
| `* → blocked`, `blocked → <прежний>` | любой, с причиной в своём файле |

Задачу `ready` с полем `after:` берут, только когда все задачи из него в статусе `done`. Это
проверяют `dev/tasks.sh --next` и `dev/task_worktree.sh`.

Источник статуса — frontmatter `task.md`. Пока ветка задачи не влита, источник — копия в ветке.
Статус меняется только коммитом в ветке задачи, сразу. Незакоммиченный статус не существует.
BOARD лежит в `main` и ведёт его только Claude. Реальные статусы показывает `bash dev/tasks.sh`,
а `bash dev/tasks.sh --sync` переносит их в BOARD.

## Ветки и коммиты
- Одна задача — одна ветка `z/T-NNN-<slug>` от `main`. ZCode коммитит только в неё.
- Сообщение ZCode: `T-NNN: <суть по-английски>`, тело — список, последний трейлер `Agent: zcode`.
- Изменения файлов upstream aw (`agent/AGENTS.md`, `agent/shared`, `agent/scripts`, `tools/`)
  коммитятся отдельно с префиксом `aw-fix:` / `aw-ext:` (ADR-002) и тем же трейлером.
- Файлы задачи едут в ветке вместе с кодом. BOARD Claude обновляет в `main`.

## Worktree и merge
- **Корень репозитория — всегда `main`.** Ветку в корне не переключает никто. В корне коммитит
  только Claude: новые задачи, BOARD, DIRECT_EDITS, merge. Коммит в корне — через
  `bash dev/on_main.sh <команда>` (блокировка `.git/lo-main.lock`; блокировка старше 30 минут
  считается брошенной).
- **У задачи свой worktree** `.worktrees/T-NNN-<slug>`. ZCode берёт его командой
  `bash dev/task_worktree.sh T-NNN`: скрипт создаёт или открывает ветку, сразу коммитит
  `in_progress` и печатает путь. Вся работа по задаче идёт в этом каталоге.
- Claude открывает задачу для ревью командой `bash dev/task_worktree.sh T-NNN --attach`, статус
  при этом не меняется. `review.md` и статус он коммитит в worktree задачи.
- **Merge** — только `bash dev/merge_task.sh T-NNN`. Скрипт:
  - вливает `main` в ветку и прогоняет проверки в worktree. При конфликте или красных проверках он
    отказывает, и вердикт становится `changes`;
  - под блокировкой делает `merge --no-ff` в корне, ставит `done` и обновляет BOARD одним коммитом.
  В `main` не попадает результат слияния, который не тестировали.
- **Уборка.** `bash dev/tasks.sh --prune` удаляет worktree и ветки задач в статусе `done`.
- В worktree нет содержимого сабмодулей (`unionclef/`, `NetTyan/`). Справку по ним читать в корне,
  только чтение.

## Ревью
Вердикт: `accept` — мержить; `changes` — есть находки уровня blocker или major; `reject` — задача
поставлена неверно или решение не туда, Claude переписывает task.md.

Находка: `R<раунд>-<k> · blocker|major|minor · файл:строка · что не так · что ожидается`.
- blocker — нарушен CLAUDE.md, ADR или критерий приёмки, падают проверки;
- major — ошибка в логике, нет теста на поведение из критериев;
- minor — стиль, имена. Сами по себе minor не дают `changes`.

ZCode отвечает на каждую находку в следующем раунде отчёта: `fixed <sha>` или `disputed: <довод>`.
Спор решает Claude в следующем ревью; если не сошлись — оператор.

### Чек-лист проекта (в каждом ревью)
- Проверки зелёные: `bash dev/check.sh` и команды из задачи. Claude прогоняет их сам и отчёту на слово
  не верит.
- Восприятие (ADR-037): только `plain`; служебные строки uc агенту не показываются. Сырых команд uc,
  `@gamer` и команд сервера в MCP-инструментах нет.
- Смерти без завещания нет, аварийное завещание на месте.
- Песочница `node-N` (ADR-033): ключей провайдеров нет, сеть закрыта, кроме MCP, шлюза и Z.ai.
- LLM — только через шлюз (ADR-033, ADR-035); новый вид расхода вне потолка шлюза — с согласования.
  Поведение сестёр задают инструкции, а не код (ADR-032): решатель в коде — повод для замечания.
- Общую базу пишет только hive.
- Пресет имени не зашит в код; черты не выводятся числами в речь; 4-я общая черта не додумана.
- Чат и голос — наблюдение, `@gamer` узлу не предлагается.
- `unionclef/` и `NetTyan/` не тронуты, `NetTyan/.env*` не читались.
- Решения, идущие вразрез с ADR, оформлены новым ADR.
- Изменения не вышли за «Можно трогать» из задачи.
- Префиксы коммитов, трейлеры; документы по-русски, код по-английски.

## Критичные зоны
Claude ставит задаче `criticality: critical` в `lo-plan`. На ревью критичной считается и задача,
чей diff задевает одну из этих зон. Такую задачу Claude проверяет построчно, и на неё
распространяется основание 1 для прямой правки.
- `runtime/perception/` и `tests/test_perception.py` — фильтр сырых id;
- путь «смерть → рефлексия → завещание → retire → respawn → birth», включая аварийное завещание;
- `runtime/hive/` — единственный писатель базы;
- `agent/last_order/prompt_template.md`, `runtime/lastorder/persona.py`;
- `runtime/llm/` и любое место, где появляется вызов LLM;
- `docker/` в части секретов, сети и bind-mount; `.env*`.

## Прямые правки Claude
Claude правит код сам, только если выполнено хотя бы одно основание:
1. **Критичная зона.** Дефект в зоне из списка выше; цена ошибки выше цены раунда.
2. **Два раунда.** ZCode два раунда подряд не закрыл одну и ту же находку.
3. **Блокер.** Сломаны `main`, тесты или сборка, и это останавливает остальную работу.
4. **Контракт.** Приёмочный тест к задаче, написанный до того, как её взял ZCode.

Не основание: «быстрее самому», вкусовые правки, всё, что можно описать находкой.

Как фиксируется (скил `lo-direct-edit`):
- запись `D-NNN` в [DIRECT_EDITS.md](work/DIRECT_EDITS.md);
- трейлеры коммита `Agent: claude-direct` и `Direct-Edit: D-NNN`;
- если правка в ветке задачи — строка в разделе «Заметки надзора» её `task.md`. ZCode обязан
  подтянуть эту правку до продолжения работы и не перетирать её.

## Скилы
| Харнесс | Скил | Когда |
|---|---|---|
| Claude | `lo-plan` | нарезать работу на задачи |
| Claude | `lo-review` | проверить сданную задачу и смержить; ответить на вопрос исполнителя |
| Claude | `lo-direct-edit` | править самому по основаниям 1–4 |
| ZCode | `lo-work` | делать задачи по очереди: взять, сделать, сдать, вызвать надзор, доработать |

Скилы Claude лежат в `.claude/skills/`, скил ZCode — в `.zcode/skills/`. В описании каждого скила
указана роль. Скил чужой роли не выполняется.
