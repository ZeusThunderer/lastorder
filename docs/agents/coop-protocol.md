# Протокол двух агентов: ZCode исполняет, Claude проверяет

Решение — ADR-019. Этот документ — канон. Скилы ссылаются сюда и правила не пересказывают.

## Роли
| Роль | Харнесс | Делает | Не делает |
|---|---|---|---|
| worker | ZCode (Z.ai, GLM) | пишет код и тесты по задаче, сдаёт отчёт | не коммитит в `main`, не меняет статусы надзора, не ставит себе задачи |
| supervisor | Claude Code | нарезает задачи, проверяет, мержит, ведёт BOARD | не правит код сам, кроме случаев из раздела «Прямые правки» |
| оператор | человек | передаёт задачи между харнессами, решает споры | — |

Оба агента подчиняются [CLAUDE.md](../../CLAUDE.md) целиком. ZCode его сам не загружает, поэтому
[AGENTS.md](../../AGENTS.md) требует прочитать его перед работой.

## Транспорт
Файлы в git. Между харнессами задачи передаёт оператор:
1. Claude создаёт задачу (`lo-plan`), статус `ready`.
2. Оператор пишет ZCode: «возьми T-NNN». ZCode работает (`lo-take` → `lo-submit`), статус `review`.
3. Оператор пишет Claude: «проверь T-NNN». Claude проверяет (`lo-review`): `changes` → снова шаг 2,
   `accepted` → merge → `done`.

Результат, которого нет в файлах задачи или в git, не считается сделанным.

### Вызов надзора из ZCode
Для некритичных задач ZCode по своему решению вызывает Claude Code CLI сам, без оператора:
`bash dev/call_supervisor.sh plan|result T-NNN` (скил `lo-call-supervisor`).
- Модель Opus, effort medium. Права: `dontAsk`, разрешены чтение, правка файлов, `git` без push,
  reset, clean и rebase, а также `uv run` и `python tools/*`. Бюджет на вызов —
  `SUPERVISOR_BUDGET_USD`, по умолчанию 3.
- `plan` — проверка плана (`## План N` в report.md) при статусе `in_progress`. `result` — обычное
  ревью при статусе `review`, при `accept` с merge.
- Скрипт отказывает:
  - для `criticality: critical`;
  - если «Можно трогать» или diff задевают критичную зону;
  - при грязном дереве, чужой ветке или запуске из корня, а не из worktree задачи;
  - сверх лимита: 2 плана и 3 результата на задачу.
- Headless-Claude код не правит. Прямая правка, выбор оператора или `reject` дают `status: blocked`,
  `Blocked: нужен оператор — …`.
- Фиксация:
  - раунды надзора в `review.md` помечены `· headless`;
  - ZCode пишет каждый вызов (sha, вердикт, стоимость) в «Вызовы надзора» своего раунда `report.md`.

Оператор в любой момент может проверить задачу обычным путём. Headless-вердикт он может
пересмотреть новым раундом.

## Файлы
```
docs/agents/work/
  BOARD.md              таблица задач
  DIRECT_EDITS.md       журнал прямых правок Claude (только дописывать)
  _templates/           task.md, report.md, review.md
  T-NNN-<slug>/
    task.md             пишет Claude; ZCode меняет только status
    report.md           пишет ZCode, раунды дописываются
    review.md           пишет Claude, раунды дописываются
```
- Номер `T-NNN` — сквозной, трёхзначный, следующий после максимального в BOARD.
- `slug` — 2–4 английских слова через дефис.
- Раунды не переписываются: новый раунд — новый раздел `## Раунд N` в конце файла.
  Раунд N отчёта отвечает на раунд N−1 ревью.

## Статусы
| Переход | Кто |
|---|---|
| `draft → ready` | Claude, только если критерии приёмки проверяемы |
| `ready → in_progress`, `changes → in_progress` | ZCode |
| `in_progress → review` | ZCode |
| `review → changes` / `accepted` / `rejected` | Claude |
| `accepted → done` | Claude после merge |
| `* → blocked`, `blocked → <прежний>` | любой, с причиной в своём файле |

Источник статуса — frontmatter `task.md`. Пока ветка задачи не влита, источник — копия в ветке.
Статус меняется только коммитом в ветке задачи, сразу. Незакоммиченный статус не существует.
BOARD лежит в `main` и ведёт его только Claude, ZCode BOARD не трогает. Реальные статусы
показывает `bash dev/tasks.sh`, а `bash dev/tasks.sh --sync` переносит их в BOARD.

## Ветки и коммиты
- Одна задача — одна ветка `z/T-NNN-<slug>` от `main`. ZCode коммитит только в неё.
- Сообщение ZCode: `T-NNN: <суть по-английски>`, тело — список, последний трейлер `Agent: zcode`.
- Изменения файлов upstream aw (`agent/AGENTS.md`, `agent/shared`, `agent/scripts`, `tools/`)
  коммитятся отдельно с префиксом `aw-fix:` / `aw-ext:` (ADR-002) и тем же трейлером.
- Claude проверяет `git diff main...z/T-NNN-<slug>` и мержит `git merge --no-ff` с сообщением
  `Merge T-NNN: <title>`.
- Файлы задачи (`task.md`, `report.md`, `review.md`) едут в ветке вместе с кодом. BOARD Claude
  обновляет в `main`.

## Параллельная работа
Несколько задач идут одновременно: несколько сессий ZCode, ревью Claude, headless-вызовы.
Поэтому общего рабочего дерева у задач нет.
- **Корень репозитория — всегда `main`.** Ветку в корне не переключает никто. В корне работает
  только Claude: новые задачи, BOARD, DIRECT_EDITS, merge.
- **У задачи свой worktree** `.worktrees/T-NNN-<slug>` (в `.gitignore`). ZCode создаёт и берёт его
  командой `bash dev/task_worktree.sh T-NNN`. Скрипт:
  - создаёт ветку от `main` или открывает существующую;
  - сразу коммитит `ready|changes → in_progress`;
  - печатает путь.
  Вся работа по задаче, включая `uv run`, тесты и коммиты, идёт в этом каталоге.
- **Захват.** Ветку нельзя открыть в двух worktree, поэтому вторая сессия, которая возьмёт ту же
  задачу, получит отказ.
- **Claude открывает задачу для ревью** командой `bash dev/task_worktree.sh T-NNN --attach`,
  статус при этом не меняется. `review.md` и статус он коммитит в worktree задачи.
- **Merge** — только `bash dev/merge_task.sh T-NNN`:
  - влить `main` в ветку и прогнать проверки в worktree. При конфликте или красных проверках
    скрипт отказывает, и вердикт становится `changes`;
  - под блокировкой `main` выполнить `merge --no-ff` в корне, поставить статус `done` и обновить
    BOARD одним коммитом.
  В `main` не попадает результат слияния, который не тестировали.
- **Блокировка `main`** — каталог `.git/lo-main.lock`. Её берут `merge_task.sh`,
  `tasks.sh --sync` и `dev/on_main.sh <команда>`, которым Claude коммитит в корне.
  Блокировка старше 30 минут считается брошенной.
- **Уборка.** `bash dev/tasks.sh --prune` удаляет worktree и ветки задач в статусе `done`.
- В worktree нет содержимого сабмодулей (`unionclef/`, `NetTyan/`). Справку по ним читать
  в корне, только чтение.

## Ревью
Вердикт: `accept` — мержить; `changes` — есть находки уровня blocker или major; `reject` — задача
поставлена неверно или решение не туда, Claude переписывает task.md.

Находка: `R<раунд>-<k> · blocker|major|minor · файл:строка · что не так · что ожидается`.
- blocker — нарушен CLAUDE.md, ADR или критерий приёмки, падают проверки;
- major — ошибка в логике, нет теста на поведение из критериев;
- minor — стиль, имена. Сами по себе minor не дают `changes`.

ZCode отвечает на каждую находку в следующем раунде отчёта: `fixed <sha>` или `disputed: <довод>`.
Спор решает Claude в следующем ревью; если не сошлись — оператор.

### Чек-лист проекта (в каждом ревью)
- Проверки зелёные: `uv run pytest`, `python tools/check.py` и команды из задачи — Claude прогоняет сам,
  отчёту не верит на слово.
- Восприятие (ADR-020): в `masked` сырые id не попадают в промпт, тест не ослаблен; в обоих режимах
  нет служебных строк uc.
- Смерти без завещания нет, аварийное завещание на месте.
- Новых LLM-вызовов сверх шага, рефлексии, завещания, консолидации сети и болтовни в лимите нет;
  у каждого вызова указан уровень (`node` / `smart` / `jev`, ADR-023).
- Общую базу пишет только hive.
- Пресет имени не зашит в код; черты не выводятся числами в речь; 4-я общая черта не додумана.
- Чат и голос — наблюдение, `@gamer` узлу не предлагается.
- `unionclef/` и `NetTyan/` не тронуты, `NetTyan/.env*` не читались.
- Решения, идущие вразрез с ADR, оформлены новым ADR.
- Изменения не вышли за «Можно трогать» из задачи.
- Префиксы коммитов, трейлеры; документы по-русски, код по-английски.

## Критичные зоны
Задача в такой зоне получает `criticality: critical`. Claude проверяет её построчно, и на неё
распространяется основание 1 для прямой правки.
- `runtime/perception/` и `tests/test_perception.py` — фильтр сырых id;
- путь «смерть → рефлексия → завещание → retire → respawn → birth», включая аварийное завещание;
- `runtime/hive/` — единственный писатель базы;
- `agent/last_order/prompt_template.md`, `runtime/lastorder/persona.py`;
- `runtime/llm/` и любое место, где появляется вызов LLM;
- `docker/` в части секретов, сети и bind-mount; `.env*`.

## Прямые правки Claude
Claude правит код сам, только если выполнено хотя бы одно основание:
1. **Критичная зона.** Дефект в зоне из списка выше; цена ошибки выше цены раунда.
2. **Два раунда.** ZCode два раунда подряд не закрыл одну и ту же находку.
3. **Блокер.** Сломаны `main`, тесты или сборка, и это останавливает остальную работу.
4. **Контракт.** Приёмочный тест к задаче, написанный до того, как её взял ZCode.

Не основание: «быстрее самому», вкусовые правки, всё, что можно описать находкой.

Как фиксируется (скил `lo-direct-edit`):
- запись `D-NNN` в [DIRECT_EDITS.md](work/DIRECT_EDITS.md);
- трейлеры коммита `Agent: claude-direct` и `Direct-Edit: D-NNN`;
- если правка в ветке задачи — строка в разделе «Заметки надзора» её `task.md`. ZCode обязан
  подтянуть эту правку до продолжения работы и не перетирать её.

## Скилы
| Харнесс | Скил | Когда |
|---|---|---|
| Claude | `lo-plan` | нарезать работу на задачи |
| Claude | `lo-review` | проверить сданную задачу, смержить |
| Claude | `lo-direct-edit` | править самому по основаниям 1–4 |
| ZCode | `lo-take` | взять задачу `ready` / `changes` |
| ZCode | `lo-submit` | сдать задачу на проверку |
| ZCode | `lo-blocked` | задать вопрос, если задача неясна или противоречит правилам |
| ZCode | `lo-call-supervisor` | по своему решению вызвать Claude headless: проверка плана или результата, только некритичное |

Скилы Claude лежат в `.claude/skills/`, скилы ZCode — в `.zcode/skills/`. В описании каждого скила
указана роль. Скил чужой роли не выполняется.
