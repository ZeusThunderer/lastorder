# Docker-топология MVP

Решение: всё работает в контейнерах (ADR-015, записать в R2). Это заменяет ADR-007 «Python на Windows».

## Сервисы

| Сервис | Образ | Что делает |
|---|---|---|
| `mc-server` | `itzg/minecraft-server` | 1.21.11, `ONLINE_MODE=FALSE`, survival, `DIFFICULTY=easy`, обычный мир, RCON. Мир на volume `world` — один постоянный мир на всех |
| `body-N` (N=1..3) | свой `docker/body` | Java 21 + HeadlessMC + Fabric 1.21.11 + fabric-api + jar uc. Ник `LastOrder0N`, `autoConnectServer=mc-server` |
| `mind-N` | свой `docker/mind` | Python 3.12 + uv. `network_mode: service:body-N`. Цикл узла, py4j-клиент и callback-сервер на localhost |
| `hive` | тот же `docker/mind` | FastAPI: реестр узлов (сквозной номер), общая база знаний (единственный писатель, git), каталог, сводки, ротация по сроку жизни |
| `llm` | vLLM (профиль `local`) | Локальная модель на 5070 Ti, OpenAI-совместимый API. Облако подключается через переменные LiteLLM без этого сервиса |

Volumes: `world`, `knowledge` (база сети под git), `body-N` (`.minecraft`, игровая папка, настройки uc).

## Слот и узел
- Слот — это пара `body-N` + `mind-N`, она живёт постоянно. Имя в Minecraft — имя слота: `LastOrder01`.
- Узел живёт внутри `mind-N` и называется «Мисака 00007» (сквозной номер из hive, формат в конфиге).
- Смерть узла:
  1. завещание;
  2. `hive.retire`;
  3. респаун тела;
  4. `hive.birth` → следующий номер с новыми чертами.
  Контейнеры не перезапускаются, доступ к docker-сокету не нужен.
- Срок жизни без смерти — `MAX_LIFE_MIN=45`, потом RCON `/kill LastOrder0N`. Застревание тоже ведёт к принудительной смерти.

## Ресурсы
Замер — `dev/measure_resources.py` (docker stats, среднее и максимум, T-003). Хост: Docker Desktop
WSL2, 24 ГБ / 18 CPU. До T-003 (замер E1 и baseline T-003, сервер MEMORY=2G VIEW_DISTANCE=8;
тело Xmx2G/Xms512M, rd4/sd5/fps20): сервер 2,2 ГБ, тело 1,6 ГБ в покое, CPU тела ~45%.

После T-003: сервер `MEMORY=1536M`, `VIEW_DISTANCE=6`, `SIMULATION_DISTANCE=5`; тело `BODY_XMX=768M`
(дефолт и в compose, и в Dockerfile), `BODY_XMS=256M`, нативные лимиты `-XX:MaxMetaspaceSize=256M
-XX:ReservedCodeCacheSize=128M` и `MALLOC_ARENA_MAX=2`, options.txt переписывается на каждом старте
(`renderDistance:2`, `simulationDistance:5` — минимум ванили, ниже клиент молча ставит 12,
`maxFps:10`); `mem_limit` тела 2g (было 3g). Тело: 1,08–1,12 ГБ в покое после входа, ~1,10 ГБ
сразу после `body_probe --kill` (замер надзора: 1,15 ГБ среднее, 1,19 ГБ максимум — запас до бюджета мал), до 1,13 ГБ во время `@get log 3` на свежей местности — бюджет
1,2 ГБ выполняется во всех состояниях (до T-003 было 1,6 ГБ покой / 1,45 ГБ после пробы).
Сервер: ~1,5 ГБ в покое, до 1,76 ГБ после долгой эксплорации (потолок задан Xmx), до 1,7 ГБ
под генерацией чанков; CPU тела avg 30–90 % в задаче (пики — генерация чанков сервером).
Три слота плюс сервер ≈ 5,5 ГБ в худшем наблюдении: на 24 ГБ остаётся запас под hive, мозги
и jev. `tools/body_probe.py --kill` проходит целиком на финальном конфиге (T-003, 2026-10-16).
Куча 768M — впритык для длинных сессий с большой базой: ручка `BODY_XMX` в compose перекрывает
дефолт без пересборки.

## Консоль (HAPI, T-044)

Стек поднимается как обычно (`bash docker/node/up.sh`); консоль — сервис `hapi-hub`
(образ `docker/hapi/`, пин `@twsxtd/hapi` 0.30.7, `hapi hub --no-relay`, том
`hapi-data`, сети svc-1..3 + svc-lo + пустая `hapi-web` только для публикации
порта: в internal-сетях публикация не работает).

- Страница: `http://127.0.0.1:3006` (только loopback хоста; номер двигает
  `HAPI_PORT` в `.env`). Вход — токен: значение `HAPI_CLI_KEY` из `.env`
  (`uv run python dev/stand_keys.py init` создаёт; то же значение хаб
  переписывает себе в `settings.json` внутри тома `hapi-data`).
- `docker/node/up.sh` ключ `HAPI_CLI_KEY` пока НЕ поднимает (вне зоны T-044):
  полный стек получит хаб с пустым env-токеном, и хаб сгенерирует свой и
  перепишет в `settings.json` [проверено: T-044 r2, одноразовый контейнер] —
  вход тогда по `docker compose exec hapi-hub cat /data/settings.json`. Подъём
  ключа в up.sh — за T-043/T-045 (вписать в их задачи: файлы надзора).
- Агентов запускает CLI (`hapi pi`) в песочницах — на стенде руками через
  `dev/console_spike/hapi_agent.py`, в бою раннер и admin (T-045/T-043).
- Квота: страница и список сессий бесплатны, платит только ход агента.
- Спайк-стенд целиком (без раннеров, слот 1): `bash dev/console_spike/up_spike.sh`
  (`down` — снять). Параллельный стенд: `HAPI_PROJECT=t044 MC_HOST_PORT=25575
  HIVE_BOARD_PORT=18081 HAPI_PORT=3006 …`. [проверено: T-044, оба подъёма]

## Доска оператора (T-049)

- Страница: `http://127.0.0.1:18080/board` (только loopback хоста; номер двигает
  `HIVE_BOARD_PORT` в `.env`; 18080, потому что 8000 на хосте занят — T-042). Вход —
  Basic-auth: пароль `HIVE_OPERATOR_KEY` из `.env` (`uv run python
  dev/stand_keys.py init` создаёт), имя пользователя любое. Скрипты и curl могут
  вместо Basic-пароля слать тот же ключ заголовком `X-Operator-Key`.
- Статика без сборки — `runtime/hive/static/board.{html,js,css}` (`GET /board`),
  внешних ресурсов и CDN нет; живое обновление — SSE `/board/stream`.

## Оператор в игре (T-051)
- Вход: любой клиент Minecraft 1.21.11 с выключенной проверкой аккаунтов (offline),
  адрес хоста стенда, порт `${MC_HOST_PORT:-25565}` (опубликован на всех интерфейсах).
  Имя игрока — ровно `OPERATOR_MC_NAME` из `.env` (поднимает `docker/node/up.sh`,
  передаётся в mind-N): тогда реплики этого игрока приходят сёстрам с меткой
  `from: operator` (в `chat.line` и в `observe`), остальные игроки — по имени,
  системные строки — без `from`.
- Риск подмены имени: сервер в `ONLINE_MODE=FALSE`, имя в офлайн-режиме не
  проверяется — любой, кто дотянется до порта, может войти под именем оператора и
  получить его метку. Поэтому метка — вес наблюдения, а не право: задачи ставятся
  только на доске [источник: TASKBOARD.md раздел 13, ADR-042]. Порт открыт на всех
  интерфейсах — при запуске стенда в чужой сети считаем метку недостоверной
  [предположение: доступ извне не проверялся, конфигурация брандмауэра хоста вне
  репозитория]. Если `OPERATOR_MC_NAME` пуст или совпадает с именем слота
  (`LastOrderNN`), меток нет; совпадение со слотом пишется в лог mind одной строкой
  `operator_name.ignored` [проверено: tests/test_executor.py].

## Запуск (E1)
- `docker compose -f docker/compose.yml up -d mc-server body-1`, затем `up mind-1` — проба `tools/body_probe.py`.
- Первый старт тела качает около 540 МБ ассетов и библиотек, это занимает 4 минуты. Всё ложится в volume
  `body-N` (`/data/.minecraft`), поэтому повторный старт до входа в мир занимает около 30 с. Java берёт
  `user.home` из passwd, а не из `$HOME`, поэтому в entrypoint стоят `-Duser.home=/data` и `hmc.mcdir`.
- Без GL (`-lwjgl`) клиент работает. Ошибки OpenAL, Realms и 401 на ключ профиля при старте — норма.

## Ключи стенда
Прогон идёт с ключами: без них `docker/node/up.sh` отказывается подниматься (fail-closed R2-6),
а приём воли падает в аварийные завещания (T-032). `dev/stand_keys.py` готовит `.env`,
порядок шагов обязателен — `issue` требует поднятый шлюз, узлы — ключи в `.env`:

1. `uv run python dev/stand_keys.py init` — генерирует недостающие локальные токены
   (`GATEWAY_MASTER_KEY` с префиксом `sk-`, `GATEWAY_DB_PASSWORD`, `HIVE_MCP_LO_KEY`,
   `HIVE_NODE_KEY_1..3`, `HIVE_RUNNER_KEY_1..3`, `RCON_PASSWORD`; `secrets.token_urlsafe`).
   Существующие значения не перезаписываются, остальные строки и комментарии `.env`
   сохраняются. Вывод — только имена ключей и added/kept, значений в нём нет.
2. Ключи провайдеров (`OPENROUTER_API_KEY`, `ZAI_API_KEY`) скрипт не создаёт: их ставит
   оператор, скрипт только напишет, каких не хватает.
3. `bash docker/gateway/up.sh` — поднять шлюз.
4. `uv run python dev/stand_keys.py issue` — выпустить через шлюз недостающие виртуальные
   ключи `GATEWAY_KEY_*` (node-1..3, mind-1..3, hive, last-order; потолки ADR-035 по
   умолчанию) и дописать их в `.env`. Ключ, потерянный из `.env`, выпускается заново —
   старый живёт в шлюзе до отзыва (`dev/gateway_keys.py revoke`)
   [предположение: на живом шлюзе не проверялось, вывод из того, что выпуск только
   создаёт ключи и ничего не отзывает].
5. `bash docker/node/up.sh` — после `init` проверка R2-6 проходит без `NODE_DEV_OPEN`
   [проверено: tests/test_stand_keys.py, прогон настоящего up.sh на временном `.env`].

## Риски
- Запасной рендер — тот же образ с `BODY_RENDER=xvfb`, 854×480. Для MVP не нужен.
- Simple Voice Chat: если он стоит, без аудиоустройства падает при входе в мир. В тело его не ставим.
- Bind-mount в compose разрешает демон, а не шелл. Запускать compose с хоста из корня репозитория.
