## План 1 · 2026-10-18

Задача задевает критичную зону («любое место, где появляется вызов LLM»), поэтому план на
согласование до кода.

### Шаг 1. Замер: `dev/jev_cloud_probe.py` (новый), до основного кода
- Каталог OpenRouter (публичный `GET /api/v1/models`, без ключа): актуальный id облачной модели
  Jev (в ADR-004/027 значится `typesafe/jev-1.13`, id мог уйти).
- 100 решений на синтетических состояниях (генератор и варианты из `dev/jev_spike.py`) БЕЗ
  политики + 100 С примером политики `policy/threat.md` (~30 строк). Всего 200 вызовов,
  ориентир стоимости < $0.01 при $0.042/1M входа.
- Путь строго через шлюз (ключ — только через шлюз, ADR/задача): цикл запросов выполняется
  внутри контейнера `llm-gateway` (`docker compose exec ... python -` по stdin, паттерн
  `dev/gateway_keys.py`), мастер-ключ не покидает env контейнера, секретов в argv нет. Замер
  включает реальный сетевой путь до провайдера; внутренний хоп mind→gateway ~1 мс — отмечу в
  jev.md.
- Метрики: p50/p95 стеновой задержки, входные/выходные токены, стоимость; сторож `--max-usd`
  (по умолчанию 0.05, из критерия). Итог — в `docs/agents/jev.md` и в этом отчёте.
- Для маршрутизации через шлюз нужен tier `jev` в `docker/gateway/config.yaml` (см. «Выход за
  «Можно трогать»»).

### Шаг 2. `runtime/mind/jev.py` (новый)
- `PolicySource`: путь из `JEV_POLICY_PATH` (по умолчанию `/mind-run/policy/threat.md`), лимит
  `JEV_POLICY_MAX_CHARS` (по умолчанию 1500 ≈ 400 токенов). Перечитывается на каждый вызов
  (сестра правит живьём), нет файла/ошибка чтения → без политики; длинный — обрезается.
  Код политику не толкует: это просто текст в запросе.
- Бэкенды за одним интерфейсом `decide(state, policy, options) -> Decision` (Decision/Option —
  `runtime/ports.py`):
  - `CloudJevBackend`: `LLMClient` из `runtime/llm/client.py`, модель `JEV_MODEL`, транспорт
    `LLM_API_BASE`/`LLM_API_KEY` (виртуальный ключ mind-N уже в compose), retries=0, таймаут
    `JEV_TIMEOUT_S`, max_tokens ~120, temperature 0; ответ JSON `{"option_id", "confidence",
    "probs"}`; чужой id — ошибка → откат.
  - `LocalJevBackend`: FastJev System One `POST ${JEV_LOCAL_URL:-http://jev:8000}/v1/systemone`
    (протокол T-005: `choice`/`probabilities`/`confidence`), тот же таймаут.
- `JevGate` — владелец пола и отката: `JEV_BACKEND=cloud|local|rules` (по умолчанию `rules`,
  ADR-027 «MVP на правилах»), пол `JEV_MIN_INTERVAL_S` (по умолчанию 3 с, ADR-027) на
  инъектируемых часах; таймаут/ошибка/невалидный ответ → запись `jev.fallback` (причина) в
  `log.jsonl` и `None` вызывающему; успех → `jev.choice` (option_id, confidence, latency_ms,
  токены, cost_usd если есть). Часы инъектируемы — как во всём executor.

### Шаг 3. Подключение в C1 (`runtime/mind/executor.py`)
- В `_threat_logic` в момент появления угрозы (урон + видимый враг) код строит под-варианты из
  тех же входных данных, что сегодняшние правила: `flee` (goto в точку-уклонение), `fight`
  (strike, если враг в fight_radius_m), `keep` (держать намерение). Сырых команд uc и `@gamer`
  в вариантах нет — только рычаги кода.
- Спрашивает `JevGate.advise(...)` (синхронно в тике, ограничен `JEV_TIMEOUT_S`; пол держит
  ≤ 1 вызова в 3 с). Валидный выбор → исполняется этот манёвр; `None` → работают нынешние
  правила без изменений (ветка кода та же). Компактное состояние: hp, food, pos, held,
  ближайший враг (вид, дистанция — имена через perception `plain`), текущее намерение.
- `Executor(..., jev=None)`: без JevGate поведение байт-в-байт сегодняшнее, существующие
  тесты не меняются.

### Шаг 4. Сборка и compose
- `runtime/mind/mcp_body.py` `main()`: собирает `JevGate` из env и передаёт в `build_mind`.
- `docker/compose.yml` mind-1: `JEV_BACKEND`, `JEV_MODEL`, `JEV_TIMEOUT_S`,
  `JEV_MIN_INTERVAL_S`, `JEV_POLICY_PATH`, `JEV_POLICY_MAX_CHARS` — интерполяция
  `${JEV_*:-default}`.

### Шаг 5. `tests/test_jev_policy.py` (новый)
- Политика: читается по пути из конфига; обрезается по длине; нет файла → без политики
  (критерий 2).
- `JEV_BACKEND=cloud|local|rules`; таймаут (медленная заглушка) и ошибка (исключение,
  невалидный JSON, чужой option_id) → правила + `jev.fallback` в log.jsonl (критерий 3).
- Пол на подставных часах: 60 с тиков по 0.5 с → ≤ 20 вызовов (критерий 4).
- Интеграция с executor: выбор Jev исполняет выбранный вариант; откат неотличим от нынешних
  правил; parse JSON-ответа cloud; parse System One ответа local.
- Статика: JEV_* env у mind-1 в compose с дефолтами; tier `jev` в gateway config маршрутизируется
  на OpenRouter с `os.environ/OPENROUTER_API_KEY`.

### Выход за «Можно трогать» (прошу расширения)
1. `docker/gateway/config.yaml` — добавить tier `jev` (полное и короткое имя, как у node/smart):
   без этого облачный Jev вообще не маршрутизируется через шлюз. Обязательная часть задачи
   «зовёт через шлюз».
2. `docker/gateway/up.sh` — фикс minor-находки R1-1 из ревью T-026 (диспетчер передал её как
   опциональную): дополнить список поднимаемых переменных `GATEWAY_KEY_MIND_1`,
   `GATEWAY_KEY_HIVE`, `GATEWAY_KEY_NODE_1` (лифт по одной переменной с снятием кавычек,
   тем же способом, что уже в скрипте). Тогда `bash docker/gateway/up.sh mind-1 hive` поднимает
   потребителей с настоящими ключами. Значения не печатаются, `.env` не читается в работе,
   только скриптом-лифтом.
   Если расширение не дают — пункт 2 выпадаю, R1-1 остаётся надзору; п.1 минимален: без него
   критерий 1 (замер) и cloud-бэкенд неработоспособны.

### Риски
- Синхронный вызов в тике держит C1 до `JEV_TIMEOUT_S` (смерть/урон детектируются на следующем
  тике). Пол 3 с делает это редким; альтернатива (правила сразу, Jev уточняет следующим тиком)
  усложняет манёвры и тесты. Выбран синхронный вариант — простота и предсказуемость, цифры
  будут в jev.md.
