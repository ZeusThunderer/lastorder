# T-055. Мост py4j — порядок подъёма тела и mind, мягкая остановка, перезапуск слота одной командой

## Цель
Мост `mind-N` ↔ uc переживает обычные действия со стендом: подъём, остановку, перезапуск слота.
`mind-N` не подключается к телу, пока оно не готово, и не оставляет шлюз uc мёртвым при остановке.
Перезапуск слота — одна команда, без ручного порядка.

## Контекст
Наблюдения сессии T-052 (~1 ч простоя стенда) [источник: отчёт T-052, «Для lo-plan»]:
- (a) шлюз Java в uc умирает навсегда, если его зарегистрированного партнёра-python убили SIGKILL;
- (b) шлюз не стартует, если клиент py4j подключился во время загрузки тела. Надёжный порядок —
  «тело полностью поднято → mind стартует». `docker restart body-N` при живом `mind-N` ломает
  мост (воспроизведено 3 раза). `mind-N` живёт в сетевом пространстве тела
  (`network_mode: service:body-N`, `docker/compose.yml:162,206,248`): перезапуск тела оставляет
  `mind-N` в старом пространстве;
- (c) `AttributeError: 'NoneType' object has no attribute 'join'` при остановке callback-сервера
  после неудачной попытки — утечка сокетов. Подключение — `runtime/game/py4j_body.py:109-116`,
  разбор — `:350-362` (`gw.close`, затем `gw.shutdown_callback_server`).
- Ловушка CLAUDE.md: `gateway.close()`, не `shutdown()`.
- `unionclef/` — только чтение, jar 1.21.11 закреплён. Обновление jar — решение оператора.

## Объём
Можно трогать:
- `runtime/game/py4j_body.py`, `runtime/mind/__main__.py`, `runtime/mind/executor.py` — готовность,
  сигнал остановки, разбор;
- `docker/compose.yml` — healthcheck тела, `depends_on: condition: service_healthy`,
  `stop_grace_period`, `stop_signal`; `network_mode` не менять;
- `docker/body/` — проба готовности, если нужна;
- `dev/slot_restart.sh` — новый: перезапуск слота в правильном порядке;
- `docs/agents/unionclef-bridge.md`, `docs/agents/docker-topology.md` — ловушки и рецепт;
- `tests/`.

Нельзя трогать:
- `unionclef/` (читать можно), `NetTyan/`, `task1.md`, `.env*`

## Критерии приёмки
- [ ] Разбор (c): после неудачного подключения повторный разбор не бросает и закрывает сокеты
  callback-сервера — тест с фейковым шлюзом.
- [ ] `mind-N` по SIGTERM закрывает шлюз (`close()`), затем выходит; `stop_grace_period` в compose
  больше времени разбора. Тест обработчика сигнала.
- [ ] Готовность тела: healthcheck `body-N` проверяет, что игрок в мире (способ — в отчёте;
  если способа без подключения py4j нет — так и написать, с файл:строка из `unionclef/`).
  `mind-N` стартует после `service_healthy`.
- [ ] `dev/slot_restart.sh N`: останавливает `mind-N`, перезапускает `body-N`, ждёт готовности через
  `dev/wait_for.sh`, поднимает `mind-N`. Сухой прогон (`--dry-run`) печатает команды; один
  реальный прогон на слоте стенда — выдержка из лога `mind-N` в отчёте: мост поднялся.
- [ ] Обновления uc: в отчёте — есть ли в upstream unionclef исправления жизненного цикла шлюза
  после закреплённой версии (ссылки на коммиты или релизы). Решение не принимать.
- [ ] `bash dev/check.sh` зелёный.

## Проверки
```
bash dev/check.sh
bash dev/slot_restart.sh 1 --dry-run
```

## Ограничения
- Перед реальным прогоном сверить с оператором, чей стенд поднят; чужой стенд не трогать.
- Квота Z.ai: для проверки моста сестра не нужна, поднимать без `node-N`.
- Если понадобится менять `network_mode` или сети compose — это критичная зона, вопрос надзору.
