- `agent/last_order/will_prompt.md` (новый) — системный промпт финальной рефлексии: английский,
  ответ по-русски, плейсхолдеры `{node_name}`, `{speech_style}`, `{quirk}` (ADR-018); чисел черт
  в промпте нет намеренно — телу запрещено их называть, меньше отказов схемы.
- `runtime/lastorder/will.py` — один вызов `smart` (kind=death, вход ≤3000 токенов: сначала
  отбрасываются старейшие события), ответ проверяется (2–4 строки, без чисел черт — стемы EN/RU
  рядом с цифрой, без сырых id `minecraft:`); любой отказ (таймаут, исключение, пустой, битый
  ответ) → `emergency_will` схемы с `emergency: true`, `model: template`; последний рубеж —
  минимальный файл даже при SchemaError от сломанных полей вызывающего.
- `runtime/lastorder/lifecycle.py` — `Lifecycle.on_death` в строгом порядке: пауза (колбэк) →
  завещание → retire (или парк в `run/<slot>/pending/will-NNNNN.md`) → respawn (2 попытки, затем
  `BodyUnavailable` наверх — завещание к этому моменту сохранено) → roll → birth → наследие →
  возобновление (колбэк). Hive недоступен: парк пишется один раз, respawn выполняется, retire+birth
  повторяются с растущей паузой (2с ×2^n, потолок 60с, 30 раундов); 409 `already_retired` считается
  доставкой, после успеха pending удаляется — завещание доходит ровно один раз; перманентный 4xx
  паркует файл и не блокирует поколение; после успешного birth — ещё одна попытка доставки
  (закрытие гонки retire-недоступен→birth-успешен, чекер C-1 р.1). Ошибка пути после паузы не
  вызывает resume — восстановление за T-014.
- `dev/death_scenario.py` (новый) — стенд-сценарий приёмки (критерий 7): рождение → RCON `/kill`
  своего слота → детектор → завещание → рождение → `request_death(stuck)` → завещание → рождение;
  проверяет наследие наследника (оба завещания, причины game и stuck), serial +2, слот держит
  последнего узла, pending пуст, стоимость ≤ $0.01.
- Тесты: `tests/test_death.py` (16), `tests/test_will.py` (19), `tests/test_lifecycle.py` (14) —
  по тесту на каждое поведение критериев 1–6, включая четыре отказа LLM с подставным клиентом и
  выключаемый hive.

### Отклонения от задачи
- Команда из «Проверок» (`… run --rm mind-1 python dev/death_scenario.py`) как написанная
  работать не может: `dev/` не входит в образ mind, а compose mind-1 не передаёт LLM-переменных
  (сфера T-022/T-014). Сценарий запускается через stdin-пайп с явным `-e`-пробросом уровня smart
  и ключа провайдера — точная команда задокументирована в docstring сценария и в подсказке при
  отказе конфигурации (это и есть закрытие C-2 раунда 1 чекера).
- `python tools/check.py` в чистом Git Bash этого хоста попадает в WindowsApps-заглушку;
  использована форма задачи `uv run python tools/check.py` — зелёный.
- Live-проверка `alive()` в сценарии фильтруется по своему слоту: на стенде в volume `knowledge`
  есть живые узлы чужих слотов от прошлых прогонов.

- В predecessors-сводке на стенде видны серийники 00006–00007 от промежуточных прогонов чекера —
