## 3. Правки uc

U1. Стенд выбирается только с лучом.
- Где: `placementStand` / `adjacentStand` / `workStand` (`BlockPlaceHelper.java:813-955`).
- Что: проверка грани из цикла установки (`:360-377`) выносится в одну функцию «можно ли поставить
  с глаза E». Её зовут и цикл установки (глаз — текущий), и выбор стенда (глаз — стенд + 1.62).
  Нет стенда с лучом — сразу леса (`scaffoldBase`) или возврат клетки, без захода.
- Почему по замыслу: один источник истины для «отсюда ставится». В коде это уже требуется: «Standable is not
  reachable» (`:607`), «a stand chosen because THAT cell can see the face» (`:683`).
- Проверка: опыт 53,67,48 — нет столба и захода к 53,68,47; курсы `deploy/` со стройкой без регресса.

U2. Точки на грани — как в baritone.
- Где: цикл установки (`:360-377`).
- Что: брать `aabbSideMultipliers` из `BuilderProcess.possibleToPlace` (`baritone/.../BuilderProcess.java:498-594`):
  2 точки на боковой грани, 5 на верхней и нижней. Сейчас берётся одна точка из
  `MovementHelper.attemptToPlaceABlock`, хотя комментарий называет цикл аналогом `possibleToPlace`.
- Почему: дословный порт.
- Эффект на этом доме [предположение]: малый, нужные лучи скользящие. Польза — меньше лишних заходов вообще.

U3. Не замуровывать клетки своей очереди.
- Где: скан очереди (`:306`).
- Что: клетка C пропускается в этот тик, если после неё у соседа N из той же очереди (или из возвращённых
  этой партии) не останется открытой грани. Сначала ставится N.
- Почему: порядок — часть строителя, а не агента. Агент шлёт схему, уследить за гранями по тикам он не может.
  Аналога в baritone не нашёл [не проверено полностью].
- Проверка: Birch Cottage на ровной площадке — 0 замурованных пустот (сейчас 5).

U4. Ветка «убрать препятствие» владеет телом, как ветка копания.
- Где: `DestroyBlockTask.java:717-790` (и «снять крышку» `:748-769`).
- Что, то же, что ветка копания делает на `:816-835`:
  - снять цель и маршрут (`Nav.clearGoal`, `stopOrphanRoute`);
  - отпустить клавиши хода;
  - заявить `minerAimUntilMs` / `minerMineUntilMs`;
  - бить только стоя на земле (условие ветки копания `:791`).
- Почему: «one owner of the body at a time» — правило самого uc (`BlockPlaceHelper.java:389-399`).
- Проверка: прогон B — 0 прыжков, сбросов нет. Курсы `deploy/` с деревьями (ветка писалась для листвы).

U5. Защита — примитив по коробке, одна система.
- Где: `Py4jEntryPoint.java:1550` (`markProtectedArea`), `:2399` (`avoidBreakingRegion`).
- Что:
  - `avoidBreakingRegion` по коробке `x1..x2, y1..y2, z1..z2` (сейчас куб по радиусу);
  - `markProtectedArea` пишет и в набор altoclef `shouldAvoidBreaking`. Сейчас только в `breakDenyZones`
    tungsten, а уборку препятствия (`canClear`, `:1114`) проверяет набор altoclef.
- Почему: агент решает, где своё, мод исполняет. Это уже записано в javadoc `avoidBreakingRegion`.
- Проверка: прогон C с коробкой точно по дому.

U6. Глубина лесов — в настройку.
- Где: `scaffoldBase` (`:902`).
- Что: 6 → `TungstenConfig`, по умолчанию 6.
- Почему: «минимум хардкода». Проверка: 48,69,50 ставится с леса 7.

Порядок: U4 и U5 (копание, причина прыжков у окна) → U1 (крыша, причина бесполезных заходов) → U3 → U2, U6.
Для U4 и U1 замеры «до» уже есть (п. 2).
