# T-065. Прогон камер на стенде — три тела на Xvfb в media, цена CPU и памяти, влияние на C1

## Цель
Известно, сколько стоят три камеры на CPU в Docker: CPU и память тел и `media`, FPS записи, место на
диске за час, влияние на C1. Выбраны значения дистанции прорисовки, fps и памяти тела для камеры.

## Контекст
- ADR-045 («начать с простого»: Xvfb на CPU), T-063, T-064.
- `dev/measure_resources.py` — средние и максимум CPU и RAM по сервисам.
- Ожидание [предположение]: ~0.5 ГБ/ч на тело при 854×480; llvmpipe ×3 нагружает CPU.

## Объём
Можно трогать:
- `dev/camera_run.sh` (или `.py`) — новый: поднять стенд с камерами, ждать через `dev/wait_for.sh`,
  снять замеры, проверить `/list` и `/get`;
- `docker/compose.yml` — только значения по умолчанию для камеры (дистанция, fps, `BODY_XMX`) по итогам;
- `docs/agents/runs/<дата>-camera.md` — отчёт прогона;
- `docs/agents/docker-topology.md`.

Нельзя трогать:
- `unionclef/`, `NetTyan/`, `task1.md`, `.env*`, `runtime/`, `agent/`

## Критерии приёмки
- [ ] Прогон 30 мин на 3 слотах с `BODY_CAMERA=1`: таблица `measure_resources.py` для `body-*`,
  `mind-*`, `media`, `mc-server` в отчёте; рядом тот же прогон без камер.
- [ ] Дистанции 2, 6 и 8: память тела и кадр (по стоп-кадру из `/get`). Выбранные значения по
  умолчанию и почему.
- [ ] Влияние на C1: время реакции и ошибки тела по `log.jsonl` с камерой и без.
- [ ] Место в `footage` за час на тело; `recordDeleteAfter` удаляет старое.
- [ ] Если CPU не держит три камеры, так и записано с цифрами. Путь через GPU или Windows не строится
  (решение оператора: начать с простого).

## Проверки
```
bash dev/check.sh
bash dev/camera_run.sh --dry-run
```

## Ограничения
- Перед подъёмом сверить с оператором, чей стенд поднят; мир не пересоздавать.
- Узлы тратят квоту: прогон держать коротким, без лишних рождений.
