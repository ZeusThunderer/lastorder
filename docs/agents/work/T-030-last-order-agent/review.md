### Решение по вопросу P1 (отдельный сервис)
Принято. Отдельный сервис `last-order` на образе node лучше, чем агент внутри `hive`: у hive есть
RCON и запись базы, bash агента рядом с ними нарушает дух ADR-033. ADR-036 («рабочее место в hive»)
не нарушается: агент один, относится к подсистеме hive, базу пишет только hive через MCP LO.
«Можно трогать» расширено (см. «Заметки надзора» в `task.md`): в `docker/compose.yml` — новый сервис
`last-order`, его volume и сеть, а также список сетей `hive` и `llm-gateway`. `docker/mind/`,
`docker/node/` и `runtime/node/` не трогать, адаптер только переиспользовать.

### Находки
- P1-1 · major · сеть `last-order` · В плане сервис сидит в `default`. Там же `mc-server` с RCON
  и паролем по умолчанию `lastorder`, так что bash агента дотянется до команд сервера (ADR-033,
  CLAUDE.md «команд сервера в инструментах нет»). Нужно: отдельная `internal` сеть (например,
  `svc-lo`), к которой подключены только `last-order`, `hive` и `llm-gateway`. Проверка на стенде:
  из контейнера `last-order` `mc-server:25575` не резолвится или не доступен. Результат — в отчёт.
- P1-2 · major · `GOALS.md`, `INBOX.md` · Файлы оператора в плане лежат в записываемом рабочем
  месте. Пометка автора «оператор» (критерий 4) держится, только если агент не может их править.
  Отсюда и хрупкий базлайн «в конце сессии, чтобы свои записи не будили». Нужно: файлы оператора
  принадлежат admin (root), для uid агента они только для чтения, как ядро сестры в
  `runtime/node/workplace.py`. Свои цели сети LO ведёт через `set_goals` и память, будильник следит
  только за файлами оператора. В отчёте указать, как оператор пишет эти файлы (bind-mount каталога
  или `docker compose exec`). Тесты: агент (uid ребёнка) не может записать в `GOALS.md`/`INBOX.md`;
  правка оператора будит, запись агента в своё рабочее место не будит.
- P1-3 · major · ядро LO (`PERSONA.md` и общие файлы шаблона) · «ядро, ro» в плане ничем не
  обеспечено. Нужно то же, что у сестры (T-027): ядро при каждом `ensure_workplace` переписывается
  из образа, владелец root, режим только чтения, сессия под отдельным uid. Bootstrap идемпотентен
  для памяти агента и не идемпотентен для ядра: подмену ядра он откатывает. Тест — подменённое ядро
  восстанавливается, а `memory/` не трогается.
- P1-4 · minor · ключ шлюза · `GATEWAY_KEY_HIVE` общий с самим hive, и тогда стоимость сессий LO
  (критерий 5) от его расхода не отделить. Лучше свой ключ `GATEWAY_KEY_LO`. Если для этого нужно
  править `docker/gateway/` (вне объёма), оставь ключ hive и посчитай стоимость LO по логу сессий
  харнесса (токены и `$`). В отчёте написать, какой путь выбран.
- P1-5 · minor · сигналы будильника · Чтение `knowledge:ro` по раскладке хранилища (`base/proposals`,
  `nodes/*/will.md`) допустимо, но раскладку держи в одном модуле с константами и тестом на образце
  файлов T-028 (статус `pending` берётся из файла, не из имени). Из хранилища — только чтение.
- P1-6 · minor · отказ от лишнего · «Минимальная пауза между сессиями» — оставить, это бюджет.
  Новых видов вызовов LLM, кроме сессии LO на `smart`, не добавлять (CLAUDE.md, бюджет).
- P1-7 · note · Пробелы MCP LO (нет ответа сёстрам через Мисака-нет, нет правки общих инструкций)
  отнесены к рискам верно. В `agent/network/AGENTS.md` прямо написать, что пока доступно и что нет:
  агент не должен пытаться писать общую базу через bash.
