# T-046. Гранты — запрос выхода наружу и секрета, одобрение оператора, хранилище hive, egress-прокси

## Цель
Last Order (или оператор от её имени) может запросить грант — выход на домен или секрет, —
оператор одобряет или отклоняет, грант можно отозвать. Одобренный домен доступен её инструментам,
секрет — только им; в песочницы сестёр не попадает ни то, ни другое.

## Контекст
- ADR-041 (гранты: запрос → одобрение; уточняет ADR-033). Это примитив среды, как системный
  вызов, а не инструмент-возможность: что делать с доступом, решает Last Order.
- Образец выхода наружу — `zai-egress` (`docker/node/zai-egress.conf`: TLS passthrough по SNI,
  один домен). Нужен прокси со списком разрешённого, который меняется по грантам без пересборки.
- ADR-042 и `docs/architecture/TASKBOARD.md`, раздел 5.3:
  - запрос гранта — запись доски `kind=request` с полем `grant` (поле хранит T-042);
  - одобрение и отказ — на странице доски (T-049), значение секрета оператор вводит там же;
  - HAPI диалогов для Pi не даёт;
  - **`approved` на доске доступа не даёт**: доступ появляется только записью гранта, которую
    hive создаёт по одобрению, а отзыв меняет запись гранта, а не статус запроса
    [источник: A2A §7.6.4 — переход в `auth-required` сам по себе не авторизация].
- Механические гранты (egress, секрет) — только Last Order и её опубликованные инструменты.
  Запросы сестёр на доске — разрешения «на дело», без доступа наружу; ADR-033 для сестёр в силе.
- Открытый вопрос, решить в задаче и обосновать в отчёте: где исполняется код с секретом. Вариант
  А — секрет в окружении процесса Pi Last Order (просто, но её bash видит секрет). Вариант Б —
  отдельный сервис-исполнитель инструментов: инструмент Last Order вызывает его, секрет и выход
  наружу есть только там; сёстры могут пользоваться опубликованным инструментом, не видя секрета
  [предположение: Б нужен для T-047, когда сёстры пишут в Telegram через инструмент Last Order].

## Объём
Можно трогать:
- `runtime/hive/` — гранты: запрос, статусы, хранилище секретов, журнал; инструмент
  `request_grant(kind, what, why)` и `grants()` на сервере Last Order (`runtime/hive/mcp.py`)
- `docker/egress/` — новый прокси со списком разрешённого; `docker/compose.yml` — сервис прокси и
  сеть Last Order до него
- `dev/grant.sh`, `dev/stand_keys.py` — при нужде; `runtime/hive/board.py` — хук «одобрен
  запрос с `grant`»; `runtime/hive/static/board.*` — поле секрета при одобрении
- `agent/network/AGENTS.md` — одна-две фразы о грантах
- тесты hive
- файлы задачи

Нельзя трогать:
- `unionclef/`, `NetTyan/`, `task1.md`
- сети `node-N`: у сестёр новых выходов нет
- `.env*` руками (только через `dev/stand_keys.py`)

## Критерии приёмки
- [ ] `request_grant(kind=egress, what=<домен>, why)` и `kind=secret, what=<имя>` создают запрос
  на доске; одобрение и отказ — ключом оператора; отзыв — тест.
- [ ] Запрос `approved`, но запись гранта не создана (сбой хука) — прокси домен не пускает,
  `grants()` гранта не показывает — тест.
- [ ] Значение секрета вводит оператор при одобрении; в журналах, ленте и ответах инструментов
  его нет — тест (grep по значению).
- [ ] Прокси пускает только одобренные домены; отзыв закрывает домен без пересборки — тест или
  проверка на стенде.
- [ ] На стенде: Last Order запрашивает выход на тестовый домен и тестовый секрет, исполнитель
  одобряет, код Last Order делает HTTPS-запрос на этот домен с секретом; из `node-1` тот же домен
  недоступен и секрета нет — выводы в отчёте. Настоящий Telegram не нужен.
- [ ] В отчёте выбран вариант А или Б с обоснованием.

## Ограничения
- ADR-033 в силе для сестёр полностью; грант — только для Last Order и её опубликованных
  инструментов.
- Общую базу пишет только hive. Секреты — не в git и не в базе знаний.
- Инструментов-возможностей (Telegram и т. п.) не писать — только механизм.
