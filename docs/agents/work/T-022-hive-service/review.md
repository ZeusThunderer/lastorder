# T-022. Ревью надзора

## План 1 · 2026-10-17 · вердикт: revise · headless
Проверено: `report.md` «План 1» @ d9ab828, сверено с `runtime/knowledge/store.py`, `schema.py`,
NETWORK.md §7/§9, GOALS_COMMS.md §3, ADR-024/026. Пересечений по файлам с задачами в работе нет
(T-009 — только perception).

Общая схема плана принята: эндпоинты 1:1 с портами, единая схема ошибок, `lifecycle.json` и
`events.jsonl` в volume `hive-run`, чтение birth.json парсером `BirthFile` (только чтение,
допустимо), `stale` атрибутом клиента (payload'ы портов frozen — допустимо), self-extra
`last-order[hive]` в dev-группе (pyproject в «Можно трогать» — принято).

### Находки
- P1-1 · major · `docker/mind/Dockerfile` · В `python:3.12-slim` нет `git`, а `KnowledgeStore`
  по умолчанию (`git=True`) делает `git init` и коммит на каждую операцию — hive упадёт на старте.
  План не упоминает git. · Установить `git` в образ (`apt-get install --no-install-recommends git`,
  это «зависимость для hive»); корень базы — из env (например `KNOWLEDGE_DIR=/data/knowledge`) на
  volume `knowledge`, volume объявить в `volumes:`. В выводе стенда для отчёта — `git -C <корень> log
  --oneline | head` до и после рестарта hive.
- P1-2 · major · `runtime/hive/lifecycle.py` · `lost` хранится только в `lifecycle.json`: у узла
  остаётся birth.json без will.md, `store.alive()` и `_require_alive` навсегда считают его живым
  (его serial по-прежнему может писать core memory, кандидаты, голоса), и это смерть без завещания
  (CLAUDE.md). · При пометке `lost` hive закрывает узел в хранилище: `emergency_will(...)` из
  `runtime/knowledge/schema.py` → `store.retire(serial, "game", text)` (причина `lost` не входит в
  `CAUSES`; факт `lost` — в событии `life.lost`). Имя узла и обращение к наследнику — по пресету из
  конфига (ADR-018), не зашивать. То же при сверке на старте. Тест: после повторного `birth` в слоте
  прежний serial есть в will.md с `emergency: true`, отсутствует в `alive()`, его запись через API
  отвергается.
- P1-3 · major · `runtime/hive/client.py` · Порядок доливки против `retire`. По §9 после
  восстановления hive мозг делает `retire`; если `retire` пройдёт раньше, чем буфер этого узла
  дольётся, все его кандидаты, голоса и core memory получат `AlreadyRetired` (4xx) и будут
  отброшены — критерий «доливаются по порядку» нарушен, знания умершего узла теряются. · Любой
  успешный вызов к hive (и `retire` обязательно) сначала досылает буфер; `retire`, `birth`,
  `request_death` не буферизуются и при недоступном hive бросают `HiveUnavailable` (завещание
  локально держит T-013). Тест: буфер с кандидатом → сервер вернулся → `retire` → кандидат в базе.
- P1-4 · major · `runtime/hive/app.py`, `lifecycle.py` · Конкурентность не описана: sync-эндпоинты
  FastAPI идут в пуле потоков, фоновый скан — в event loop; `lifecycle.json`, inbox в памяти и пара
  «пометить lost + новый birth» в одном слоте меняются из разных потоков. · Один lock на состояние
  Lifecycle и inbox; `birth` в слоте атомарен под ним; блокирующий RCON и store в скане — через
  `asyncio.to_thread` (не держать loop); uvicorn строго с одним воркером (в compose явно
  `--workers 1`, комментарий почему). Тест: два параллельных `birth` в один слот дают ровно один
  живой узел и один `lost`.
- P1-5 · minor · `runtime/hive/app.py` · Классы ошибок для клиента: доливка отбрасывает 4xx, значит
  временные отказы хранилища (`StoreError("knowledge base lock timeout")`, `git failed`) не должны
  уходить в 4xx. · Явная таблица: `UnknownNodeError` → 404, `AlreadyRetiredError` → 409,
  `Invalid*Error`/422 валидации → 422, прочие `StoreError` → 503 (клиент повторяет, не отбрасывает).
  Отброшенную при доливке операцию клиент пишет событием, а не молча.
- P1-6 · minor · `runtime/hive/lifecycle.py` · RCON `/kill` на офлайн-игрока отвечает текстом
  «No entity was found», транспорт при этом успешен — узел будет помечен «убит» и проживёт сколько
  угодно. · Успех — только по ответу сервера об убийстве; иначе `life.rcon_failed` и повтор на
  следующем проходе. Причину `ttl` в `retire` подставлять только после подтверждённого kill. Тест
  с подставным RCON на оба ответа. `request_death` с причиной ≠ `stuck` → 422; неизвестный или
  мёртвый serial → 404/409 без RCON.
- P1-7 · minor · `runtime/hive/client.py` · Повтор `send` после таймаута чтения (запрос дошёл, ответ
  потерян) дублирует сообщение; для кандидатов, голосов и core memory хранилище идемпотентно
  (evidence узла, замена голоса, перезапись). · Для записей повторять сразу только при ошибке
  соединения; при таймауте ответа — в буфер с `op_id`, hive помнит последние `op_id` `send` и
  повтор не кладёт. Или назвать дубль допустимым в отчёте — выбор за исполнителем.
- P1-8 · minor · `runtime/hive/app.py` · Адресат `all` (GOALS_COMMS §3) в `NodeMessage.to_serial: int`
  не выражается. · Не вводить молча: либо явно «broadcast — T-017» в отчёте, либо отдельный
  эндпоинт/константа с тестом. Путь буфера клиента — из env (`RUN_DIR`), у `mind-1` volume `run`
  пока нет, а другие сервисы compose трогать нельзя — указать в отчёте.
- P1-9 · minor · тесты · Пароль RCON: проверить тестом, что ни `events.jsonl`, ни лог, ни repr
  клиента RCON его не содержат. Фильтр сырых id: тест API, что кандидат с `minecraft:…` → 422 в
  единой схеме и при доливке не повторяется бесконечно. `leak_check` хранилища в hive остаётся
  `None` (словарь сырых id есть только у perception мозга) — одной строкой в отчёте.
- P1-10 · minor · отчёт · Праймер грузится только в свежую базу; volume `knowledge`, созданный
  сейчас, без праймера T-010 его уже не получит. В T-022 не чинить — отметить в отчёте как риск
  для T-010.
