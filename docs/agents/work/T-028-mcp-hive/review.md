## План 1 · 2026-10-18 · вердикт: revise · headless

Сверено с task.md, NETWORK.md v2 §4–§7, `runtime/hive/lifecycle.py` (`require_node`, `retire`),

Решение по шагу 2: расширение `runtime/knowledge/` (`Record.decision`, `status_of(decision=)`,
`KnowledgeStore.apply_decision`, `KnowledgeStore.commit_layer`) одобрено как часть «Можно трогать»:
это сохраняет единственного git-писателя. Условие: `commit_layer` принимает пути только внутри
`base/` (proposals, skills, instructions.md, goals.md, chronicle.md); путь вне — отказ, тест.

- P1-1 · major · шаг 4, идентификация · Карта `HIVE_MCP_NODE_KEYS` вида `7=sk-a;8=sk-b` задаётся
  в env при старте hive, а номера узлов выдаются при рождении, сквозные (00007 → 00008 в том же
  слоте). Статическая карта «номер → ключ» не знает будущих номеров. Ключи шлюза в T-026 — по
  слоту. Нужно: ключ → слот (`slot=key`), номер — текущий живой узел этого слота из
  `Lifecycle` (`alive()`/состояние слота). Тест: рождение нового номера в слоте — тот же ключ
  даёт новый номер, старый номер этим ключом недоступен.
- P1-2 · major · шаг 4, идентификация · «Ключ **или** заголовок `X-Runner-Node`»: заголовок без
  секрета ставит кто угодно в песочнице `node-N` (раннер и харнесс там вместе, ADR-033), и
  «чужой номер — отказ» не проверяется. Нужно: личность только по ключу; `X-Runner-Node`, если
  есть, — лишь сверка с номером из ключа (не совпал — отказ). Тест: заголовок с чужим номером без
  ключа и с чужим ключом — отказ.
- P1-3 · major · шаг 4, `submit_will` · Критерий — «только для умершей сестры». В плане проверка —
  заголовок `X-Runner-Session: will`, который агент в той же песочнице может выставить сам при
  жизни; к тому же общая проверка «номер умершей — отказ» противоречит `submit_will`, где номер
  как раз умерший. Нужно: у `submit_will` своя проверка — узел ещё не retired, а факт смерти
  известен hive (отметка `dead` в `Lifecycle` от сигнала смерти — `kill_confirmed`/новый
  `mark_dead`, если сигнала пока нет — заглушка-метод с тестом, разводка от `mind-N` в T-027);
  заголовок сессии — дополнительное условие, не единственное. Живой узел с заголовком `will` —
  отказ, тест. Если отметку смерти в hive без правки вне «Можно трогать» не сделать — `lo-blocked`
  с вопросом, а не обход.
- P1-4 · minor · шаг 3, `decide` · «Под git с автором и причиной»: в плане автор и причина лежат
  в proposal-файле. Пусть сообщение коммита тоже их несёт (`decide p-NNNN accept by last_order:
  <why>; proposer 00007`), тест читает `git log`.
- P1-5 · minor · шаг 3, инструкции · `base/instructions.md` — новый общий слой. В отчёте явно
  отметить, что доставку его в рабочее место сестры делает T-027/T-029, иначе принятая правка
  никем не читается. Ядро (`agent/last_order/prompt_template.md` и `agent/*/` вообще) — вне `base/`,
  отказ по пути уже есть в тестах плана — оставить.
- P1-6 · minor · шаг 4, `vote` · В плане не сказано, что делает `vote`: ожидаю обёртку над
  существующим `HiveService.submit_vote` (`Vote`) без новой логики; голос за своё предложение —
  как решает текущий store, отдельно не изобретать.

Остальное (два отдельных сервера вместо отказа в рантайме, lifespan через `AsyncExitStack`,
настоящий streamable HTTP в тестах, лимит `send` 160, dedup как есть) — принято. После правки
P1-1…P1-3 в `## План 2` — повторное ревью плана не обязательно, если правки сделаны ровно так;
иначе — новое ревью.

### Находки
- R1-1 · major · `runtime/knowledge/store.py:573`, `runtime/knowledge/store.py:612` · `submit_candidate`
  (дубль → evidence) и `submit_vote` пересчитывают статус через `status_of(...)` без `decision`. Поле
  `decision` в записи остаётся, но статус считается так, будто решения нет. Сценарии: (а) Last Order принял
  знание (confirmed), одна сестра голосует против с причиной — запись становится `disputed`, две — `retired`;
  (б) принятый навык (`kind=skill`, confirmed, без evidence) после любого голоса падает в `hypothesis`
  или ниже. Это противоречит собственному контракту `status_of` («a decision settles the record… above
  refuters and evidence») и NETWORK §7. Ожидается: оба вызова передают `record.decision` /
  `duplicate.decision`. Голоса и evidence после решения по-прежнему пишутся, а статус остаётся решённым.
  Тест: accept → два опровержения → `confirmed`; принятый навык → голос → `confirmed`; дубль решённой записи → статус прежний.
- R1-2 · minor · `runtime/hive/proposals.py:185` · Хунк чистой вставки `@@ -N,0 +M,K @@` (вывод
  `diff -U0`) по смыслу unified diff вставляет строки **после** строки N, а код вставляет перед ней
  (`start = old_start - 1`). Контекстные диффы (difflib, `-U3`) это не задевает. Ожидается: при пустом
  `old_lines` и `old_start > 0` — `start = old_start`, плюс тест на `-U0`.
- R1-3 · minor · `runtime/hive/lifecycle.py:260` · У `mark_dead` нет вызова через HTTP. `mind-N` и раннер
  живут в других контейнерах, поэтому T-027 понадобится расширение порта (`POST /registry/mark_dead`).
  Пока его нет, `submit_will` при естественной смерти недостижим, и путь всегда уходит в аварийное
  завещание раннера. Аварийный путь цел: регрессии нет, план это согласовал. Отметить в отчёте как
  точку интеграции T-027; можно добавить endpoint здесь, «расширять можно».
