## Раунд 2 (review R1-1, R1-2)

- **«Мысль» как реплика самого агента — НЕ достижима расширением (Pi 1.4.0):** оба
  пути кладут `custom`-запись, модель читает её как внешнюю строку:
  `pi.sendMessage({role:"assistant",…})` → в сессии `role: custom` [проверено:
  session5]; возврат `{message:{role:"assistant",…}}` из обработчика
  `before_agent_start` → тоже `role: custom`, модель: «they provide "Operator's
  thought…"» [проверено: session6]. Расширение — `dev/console_spike/thought.ts`
  (обе команды: `/thought`, `/thought2`). Вместо этого: событие
  `before_provider_request` — расширение правит запрос к модели непосредственно
  перед отправкой и может вставить настоящее assistant-сообщение [источник:
  docs/extensions.md; не прогонял: лимит сессий 5/6]. Для «голоса извне»
  (наблюдение) custom-строки достаточно, для «мысли» — нет.
- **Путь оператора из консоли (R1-2):** сервис `console-pi-web-ui` несёт те же
  конфиги узла (рендер `drop_pi_agent_dir` в `/root/.pi/agent` [проверено:
  models.json/mcp.json/settings.json на месте, get_state → zai/glm-5.3-flash]),
  сеть slot-1 (тело) + default (hive) и ключ Z.ai в env процесса [проверено:
  entrypoint-материализация]. Беседа в UI спавнит pi с инструментами body/hive —
  до границы консоли проверено, клик в браузере не автоматизировался (HTTP API
  списков/отправки не публикуется: очевидные пути 404) [проверено].
- **Сессия, запущенная не консолью:** консоль сканирует свой session-dir
  (`/root/.pi/agent/sessions`); сессии, созданные нашим RPC-процессом в её
  контейнере, попадают в тот же каталог, но оставшийся LLM-лимит не позволил
  оставить валидную сессию-файл и увидеть её в UI — клетка остаётся
  [источник: docs] + проверка оператором по рецепту ниже.

## Прогоны на стенде (T-041)

- **pi-web-ui** — `[проверено]`: поднялся сервисом профиля `console-spike`
  (`console-pi-web-ui`, пин 0.111.0; нужны `make`/`g++` для node-pty — ставятся при
  старте), `GET /` → 200, `GET /api/health` → 200, внутри pi SDK v1.4.0, сессии в
  `~/.pi/agent/sessions`. Пакет пинится в compose (review R1-3), консоль сидит в
  своей сети `console-spike` + slot-1 (тело) + default (только hive).
- **pi-web (jmfederico)** — `[проверено]`: в контейнере не поднимается: `pi-web install`
  требует `systemd-run`, `pi-web start` — `systemctl --user` (лог в отчёте T-041).
  Сервис оставлен в compose для воспроизведения.
- **HAPI, Epsilondelta-ai/pi-web** — по документации с пометками.

## Рекомендация

**pi-web-ui** — единственный из четырёх, который поднялся на стенде в контейнере, при
MIT-лицензии, опциональном токене и мультибеседности; **но** ни один кандидат (включая
его) не прицепляется к сессии Pi, запущенной нашим раннером в `node-N`: готовые консоли
сами спавнят локального pi. Для ADR-041 это значит: «оператор пишет сестре в node-1»
нужен мост (наш RPC-прокси/расширение против консольного pi) либо консоль остаётся
инструментом оператора рядом с его собственным pi, а не терминалом сети. Выбор за
надзором и оператором; данные — выше.

## Рецепт оператора (T-041; проверен исполнителем до границы UI)

Сервисы `console-pi-web-ui`/`console-pi-web` удалены в T-044 (ADR-042); воспроизвести
находки T-041 можно по коммиту до T-044. Текущий рецепт консоли — в
[docs/agents/docker-topology.md](docker-topology.md), раздел «Консоль».

```bash
# одна RPC-сессия Pi в node-1 вручную (это тоже квота):
MSYS_NO_PATHCONV=1 docker exec -i -e PI_TIMEOUT_S=120 \
  -e "PI_PROMPT=Ответь одним словом: связь" node1-pi \
  /app/.venv/bin/python - < dev/console_spike/pi_rpc.py
```

## Итог: HAPI (ADR-042, T-044)

Стенд: `hapi-hub` (свой образ `docker/hapi/`, пин `@twsxtd/hapi` 0.30.7, `hapi hub
--no-relay`), CLI HAPI — слой в `docker/node/Dockerfile`. Подъём и рецепт —
[docs/agents/docker-topology.md](docker-topology.md), раздел «Консоль».

- **Два агента на одной странице** [проверено: T-044]: `hapi pi` от uid `sister` в
  `node-1` (конфиги слота — `drop_pi_agent_dir`, zai + MCP body/hive) и второй
  тестовый агент в песочнице `last-order` (минимальный конфиг, провайдер — шлюз);
  оба видны в одном списке `GET /api/sessions` с машинами, моделями и статусами.
  Переключение бесед — SPA той же страницы [источник: web-ассеты хаба]; кликами в
  браузере не проверял — проверял REST-данные страницы.
- **Чат оператора** [проверено: T-044]: по одному сообщению каждому агенту через
  `POST /api/sessions/:id/messages` (тот же путь, что страница); агент node-1 вызвал
  `mcp__body__observe` и ответил, LO-агент ответил через шлюз.
- **Запуск без TTY** [проверено: T-044]: `hapi pi` от `su sister` с stdin=/dev/null;
  аргументов Pi не нужно — конфиги берутся из `~/.pi/agent`, HAPI добавляет только
  своё title-расширение флагом `--extension`. Флага «первое сообщение» нет
  [источник: cli/src/commands/agentCommandOptions.ts]: веб (оператор), REST POST в
  сессию [проверено: сообщение дошло и было отвечено] или расширение Pi при старте.
- **Токен входа** = `HAPI_CLI_KEY` из `.env` (`stand_keys init`); им же
  аутентифицируется CLI сестёр (`CLI_API_TOKEN` env) [проверено: T-044].
- **Граница токена** [проверено: T-044]: с базовым токеном из bash сестры — логин
  веб-пользователем, список ВСЕХ сессий, чтение и запись в чужую сессию (сообщение
  от имени оператора дошло и было отвечено), `hapi inspect-peer`/`ping-peer` — то
  же по CLI. Remote spawn невозможен, пока в `node-N` нет `hapi runner`
  (`GET /api/machines` пуст). Namespace-суффикс `<token>:node-1` изолирует сестру
  (0 чужих сессий), но тогда оператор не видит её на своей странице — выбор за
  оператором, эскалация в задаче T-044.
- **Сессия после смерти** [проверено: T-044]: процесс убит — хаб быстро помечает
  сессию неактивной, транскрипт остаётся читаемым; кнопка resume возвращает успех,
  но без раннера ничего не поднимает; нативный resume — `hapi pi --session-id …`
  на стороне машины (это раннер T-045, не HAPI).
- **Файл сессии Pi** [проверено: T-044]: `~/.pi/agent/sessions/<slug>/*.jsonl`, в
  каждой assistant-записи `usage` (input/output/cache/total) — учёт для адаптера
  есть; `/session` в чате печатает сводку.
