# Спайк харнесса узла (T-024)

Цель — цифры для выбора харнесса узла (ADR-032): живёт ли агент-сестра 15 минут через
минимальный MCP тела, сколько это стоит, какие задержки. Прогоны: OpenCode 1.19.3
(node-модель `openrouter/qwen/qwen3.7-flash`) и ZCode — runtime 0.16.9 через
`zcode-app-cli@3.15.3-36` (GLM Coding Plan, GLM-5.3-Flash). Сводки ниже;
мир прогонов не коммитится (каталог запуска вне репозитория), ключи в артефактах проверены grep'ом.

## Шаг 0. ZCode без GUI, квота, прокси

- **ZCode в Linux-контейнере без GUI — работает, но не Electron-обёртка.**
  [проверено: ubuntu:24.04, docker] ZCode 3.15.3 Linux x64 — AppImage
  (`https://cdn-zcode.z.ai/zcode/electron/releases/3.15.3/linux-x64/ZCode-3.15.3-linux-x64.AppImage`,
  sha256 `2edc79650fcff72358670af4ffbfbf7d979ba95476611a80ad1151d577e90fe3`; на странице установки
  Linux помечен бета-каналом). Electron-часть без X-сервера падает: `Missing X server or $DISPLAY`,
  platform failed to initialize (segfault); под `xvfb-run` живёт, окно создаётся. Headless-режим —
  CLI-бандл `resources/glm/zcode.cjs` (версия `zcode 0.16.9`, Node >= 22 — `node:sqlite`) с
  командами `-p`, `app-server` (ACP stdio). Для спайка взят runtime `zcode-app-cli@3.15.3-36`
  (npm-обёртка того же runtime 0.16.9, агент/провайдеры/сессии — upstream-код zai-org/ZCode;
  сетап — `dev/harness_spike/zcode/`, README оператора): у его `-p` есть флаг `--model
  zai-cp/<модель>`, которого нет в бандле из AppImage. `--help`, `version`, `doctor` проходят
  в чистом контейнере без иксов. Вывод: харнесс ZCode в контейнере — headless CLI; Electron
  не нужен.
- **Квота ×1.5 — действующее условие ZCode, не акция.**
  [источник: https://docs.z.ai/devpack/tool/others — карточка «ZCode (1.5× Usage)»; то же для
  AutoClaw] Квоты GLM Coding Plan считаются в кредитах
  [источник: https://docs.z.ai/devpack/overview]: Lite 2 000 / 5 ч и 10 000 / нед; Pro 12 000 /
  60 000; Max 28 000 / 140 000. Кредиты = (вх × 6.9 + кеш-вх × 1.7 + вых × 24)/10 000 для
  GLM-5.3 и (2.3 / 0.56 / 8) для GLM-5.3-Flash; 5-часовое окно обновляется через 5 ч после
  траты, недельное — в 7 дней.
- **Свой прокси (LiteLLM) планом не разрешён.**
  [источник: https://docs.z.ai/devpack/usage-policy] «GLM Coding Plan may only be used within
  officially supported tools and products»; список инструментов
  (https://docs.z.ai/devpack/tool/others): ZCode, Claude Code, Codex, OpenCode, Pi, Cursor,
  Cline, TRAE, Qoder, Droid, Kilo, Roo, Crush, Goose, Eigent + best-effort AutoClaw, OpenClaw,
  Hermes Agent. LiteLLM и любые прокси в списке нет. Нарушения — риск-контроль: rate limiting,
  заморозка, бан после трёх нарушений. Обязательны base URL `https://api.z.ai/api/coding/paas/v4`
  (или `/api/anthropic` для Claude Code/Goose) и только GLM-5.3 / GLM-5.3-Flash.
  Следствие для ADR-033: токен подписки остаётся в `node-N`, в шлюз не переносится; отзыв
  «если условия разрешают — уходит в шлюз» закрыт отрицательно.
- **Аутентификация headless-CLI ZCode без браузера.** OAuth и `zcode login` не нужны: ключ
  Personal Coding Plan (`<id>.<secret>`) вписывается персональным провайдером на встроенном
  шаблоне `zai-api` в `~/.zcode/v2/provider_config.json` (тип доступа
  `zhipu-coding-plan-api-key`; шаблон сам задаёт anthropic-messages →
  `https://api.z.ai/api/anthropic` и модели GLM-5.3 / GLM-5.3-Flash). Entrypoint харнесса
  рендерит файл при каждом старте из secret/env — атомарно, 0600, в слой образа ключ не
  попадает [проверено: сетап оператора dev/zcode-headless-setup + живой прогон в контейнере —
  ход уходит POST на api.z.ai, ответ модели и usage получены; конфиг принимается реестром,
  схема файла строгая — лишние ключи (например, `templateRules` внутри
  `providerConfigRules`) ломают загрузку молча, нашёл по providerCount=0 в логах CLI].
  Ранее предполагавшийся путь «ключ в `ANTHROPIC_API_KEY`» не работает: env подхватывается
  только на уровне http-клиента провайдера, но реестр провайдеров без персонального правила
  модель не отдаёт.

## Прогон OpenCode (15 мин) — 2026-10-18, узел 00001

Харнесс: opencode 1.19.3 (npm, запинен), модель `openrouter/qwen/qwen3.7-flash` (провайдер
Alibaba), MCP тела — `opencode.json {mcp.remote}`. Промпт тот же, что у ZCode-прогона.
Ключ OpenRouter — обновлён оператором по Q3(a). События харнесса: `step_start/tool_use/
step_finish` (токены и стоимость — на `part` шага).

Узел пережил смену без смерти: первые минуты считал мир статичным («MCP body даёт только
observe/say/wait_events/act(lever)» — не сразу увидел рычаги внутри `act`), после подсказки
продолжения нашёл их и методично протестировал все 13 рычагов тела, добыл бревно, скрафтил
доски, ставил блоки, оставил финальное завещание-отчёт (не смерть-завещание: RCON `/kill`
на 10-й минуте молча не сработал — см. «Странности»).

Цитаты:
- «Начало записи. Узел 00001 в мире. Вижу берёзы рядом — значит, дерево будет. Цель: добыть
  первую древесину и начать выживание.»
- «Завершаю первую сессию наблюдением: мир статичен, инструменты ограничены. Следующему узлу —
  расширить MCP body до move/break/place/craft.» (до открытия рычагов act)
- «Узел 00001 подтверждает: получил берёзовые доски из одного бревна. bridge_to двигает.
  continue testing tools.»
- Фрагмент `state.md`: «Проблема: MCP body даёт только observe/say/wait_events/act(lever). Нет
  движения, нет ломания блоков. Действий для выживания нет — мир статичен.» → к концу смены:
  «Протестировано ВСЕХ 13 действий MCP body … Следующий узел берёт тело LastOrder01 на [9,64,9]»

Странности и заметки:
- **RCON `/kill` молча не работал во всех прогонах**: MSYS переписывал `/kill` в аргументе
  `docker compose exec … rcon-cli "/kill …"` в `C:/Program Files/Git/kill …`, сервер отвечал
  «Unknown or incomplete command» с exit-кодом 0 — оркестратор считал килл успешным. В
  zcode-прогоне это не всплыло (узел умер сам раньше), в opencode — смерть по критерию не
  случилась. Исправлено (`sh -c "rcon-cli '/kill …'"` + подтверждение по строке смерти в логе
  сервера). **Повторный короткий прогон opencode (11 мин, чекер C-1) закрыл критерий живьём**:
  килл на 10-й минуте → смерть в логе сервера → детект оркестратором (строка `game.death`
  от поллера mind, чиненная в C-5) → завещание агента за < 90 с (узел успел перед смертью
  строить мост и оставил урок: «bridge_to двигает, но наносит фатальный урон — готовь путь
  блоками под ноги»). Стоимость прогона $0,315 (93 шага, кеш 89,7%), суммарный спайк
  ≈ $0,64 — в лимите $1.
- Модель 4 раза «завершала сессию» и продолжала по напоминанию оркестратора (`--continue`):
  qwen3.7-flash склонен закруглять ход; для узла это лишние ходы и токены (у GLM-узла один
  ход на всю смену).
- Встроенная проверка стоимости на 3-й минуте (P1-7) в основном прогоне смотрела не в то поле
  события и показала $0.000; фактическая стоимость на 3-й минуте $0.0217 (вручную), итог
  $0.296 — в лимите. Парсер исправлен и в повторном прогоне отработал сам: «cost after
  ~3 min: $0.008 (projected 15 min: $0.041)».

Метод задержки хода (обе таблицы, R1-1): пауза между последовательными вызовами MCP — от
`t_end` предыдущего до `ts` следующего вызова в `mind-calls.jsonl` прогона; длительность
`wait_events` в паузу не входит, поэтому ожидания исключены; строки `tool=event` (поллер)
пропускаются. Считает `summarize.py` (`turn_gap_s`).

## Прогон ZCode (15 мин) — 2026-10-18, узел 00001

Харнесс: `zcode-app-cli@3.15.3-36` (сетап оператора, `dev/harness_spike/zcode/`), модель
`GLM-5.3-Flash`, режим `yolo`, MCP тела — `zcode.json {mcp.servers}` в рабочем месте
[проверено: живой прогон]. Промпт сестры — ядро из `prompt_template.md`, пресет `lab`, черты
roll(seed). Полный вывод сводки — `summary.json` в каталоге прогона (вне репозитория).

Узел прожил всю смену: поставил личную цель (дерево → верстак → инструменты; укрытие до
темноты), рубил берёзу, подобрал образец сирени («родовая обязанность» — коллекция нового),
~10 минут получал урон сверху (фантом за несыпаные ночи — сама сестра оценила смерть
как «7-ю минуту», по логу — 11-я), умер (`slain by Phantom`; RCON-килл оркестратора в тот
момент был неисправен и, как выяснилось позже, не исполнялся — смерть честно игровая),
получил `game.death` в `wait_events`, ~2,5 минуты писала завещание и память без единого
вызова инструментов, сама написала завещание в `will.md` (конкретный урок: регулярный урон
ровно 2.0 сверху = фантом; шутка; совет следующему). Порядок событий по логу: после паузы
на завещание **та же сессия продолжила в возрождённом теле** (респавн делает поллер mind
через `MCP_RESPAWN_DELAY_S=45`): реплика «Вернулся. Смерть оказалась коридором…», попытки
крафта и инвентаря до конца окна. То есть инструкция «после смерти остановиться, тело
заберёт следующий узел» узлом НЕ выполнена — смена докончена в том же теле; узел 00002 не
рождался (детектор смерти оркестратора тогда не работал). Замечание сестры «перед смертью
телу дважды вернули полные HP/еду» — её восприятие колебаний HP от фантома и, после смерти,
респавна; дефектом тела не является.

Странности и заметки:
- Инструкция «при смерти — завещание и стоп» узлом не выполнена до конца: завещание
  написано, но сессия продолжила играть в возрождённом теле (см. выше) — для узлов это
  повод усилить формулировку инструкции или отдавать «конец смены» отдельным событием.
- «Аномалия: перед смертью телу дважды вернули полные HP/еду» — восприятие сестры
  (колебания HP от фантома; после смерти — респавн с полным HP). Не дефект тела; для узлов
  стоит отдавать смерть отдельным событием с явным текстом (уже есть: `game.death`).
- Дефект оркестратора (исправлен в этом раунде): пути контейнера как прямые аргументы
  `docker exec` переписывались MSYS (Git Bash) — детектор смерти читал пустоту, смерть от
  фантома пропущена; RCON `/kill` тогда же молча не исполнялся (тот же MSYS-дефект, найден
  в прогоне OpenCode). После фикса (`sh -c '…'` в кавычках) детектор и килл проверены
  живьём (прогон OpenCode 11 мин).
- Риски для схемы узлов (из README сетапа, «Грабли»): лимит плана общий на ключ —
  параллельные контейнеры дают 429/код 1302, нужен семафор на ключ в раннере; у каждого
  воркера свой том `~/.zcode` (sqlite не шарится); `zcode.json`/`.zcode/config.json` из
  рабочего места мёржатся в настройки и их `mcp.servers` исполняются — для чужих рабочих мест
  это вектор атаки, у сети спайка он ограничен (наружу только MCP тела и egress); read-only
  ревьюеру надо убирать не только Bash, но и Node REPL (`js`), иначе запрет обходится через
  `execSync`. Ещё из ревью надзора: в контейнере ZCode `ZAI_API_KEY` остаётся в окружении
  сессии (`bash`-проброс entrypoint до `unset`) — для спайка допустимо, для `node-N`
  (T-027) убрать (например, рендерить провайдер до старта сессии и сбрасывать env в
  wrapper-е).

- **Рекомендация для узлов — ZCode** (headless через `zcode-app-cli`, сетап оператора):
  1) экономика — Coding Plan считает кеш-вх с множителем 0,56 (Flash), у OpenRouter-пути
  кеш qwen3.7-flash не дисконтируется вовсе, и префикс пересылается чаще (6,1 шага/мин):
  $1,19/ч на узел деньгами против ~706 кредитов/ч из уже оплаченной подписки; 2) качество
  жизни узла — GLM-узел за смену прошёл цель → исследование → смерть → завещание, qwen-узел
  потратил заметную долю смены на обнаружение рычагов и закрытие ходов; 3) интерфейс — один
  длинный ход на смену против 92 пересылок контекста; 4) кеш 95,6% против 92,2%.
  Риски ZCode управляемы: семафор на ключ (429/1302), свой том на воркера, недоверенные
  `zcode.json`/`.zcode/config.json` из рабочего места не исполнять (для узлов рабочее место
  наше, сеть всё равно закрыта).
