# FastJev на RTX 2070 в Docker: как поднять и что вышло (T-005)

Статус: спайк, 2026-10-16. Сервис `jev` в compose под профилем `jev`, движок fastjev 0.2.0
(MIT), карта — RTX 2070 8 ГБ (вторая карта, 5070 Ti, сервисом не занимается). Решения: ADR-004
(FastJev в C1), ADR-023 (уровень `jev`, карта 2070). Проверяемое допущение ARCHITECTURE §8
«vLLM на Turing не используем» — подтверждено, см. «Движок».

## Поднять и проверить за 3 команды

Из корня репозитория:

```bash
docker compose -f docker/compose.yml --profile jev up -d jev   # собрать и поднять на 2070
curl -s http://127.0.0.1:8730/v1/models                        # ждём "fastjev-2070" (первые минуты — загрузка модели)
uv run python dev/jev_spike.py --n 200 --url http://127.0.0.1:8730 --gpu 0   # замер: p50/p95, доля в формате, VRAM
```

Первый запуск скачивает модель в именованный volume `lastorder_jev-hf` (~5 ГБ для MiniCPM5-2B,
минуты зависят от HuggingFace без токена). Публикация порта — только `127.0.0.1:8730` и только
ради замера с хоста; продакшн-клиенты (mind-N) ходят внутри docker-сети на `jev:8000`.
Модель и ревизия — переменными `JEV_MODEL` / `JEV_REVISION` (по умолчанию — победитель замера,
см. таблицу). Аутентификации нет: сервис за `--allow-unauthenticated` внутри compose-сети;
перед любым доступом вне docker-сети задать `FASTJEV_API_KEY` и убрать флаг.

## Что измерялось

`dev/jev_spike.py`: 200 синтетических состояний тела C2-формата (hp, food, pos, held, looking_at,
ближайший враг/пассив, событие, intent) × списки 4/8/16 вариантов — тексты вариантов это
altoclef-команды и рычаги uc (ADR-003: `@get`, `@stop`, `@food`, `mineBlock`, `punk`, `gotoXYZ`,
`selectHotbar`, `holdKey`…). На каждый размер 10 прогревочных запросов, затем 200 замеренных;
задержка — стеновое время HTTP-вызова `POST /v1/systemone` (choice). «В формате» — ответ содержит
выбор из списка, распределение по всем вариантам и confidence. Пиковая VRAM — опрос
`nvidia-smi memory.used` каждые 200 мс (попоточную статистику WSL2 не отдаёт).

## Движок: почему не vLLM (подтверждение ARCHITECTURE §8)

vLLM 0.29.0 (пин fastjev) на Turing (sm_75, RTX 2070, WSL2) падает на инициализации движка:
`RuntimeError: UVA is not available` (`vllm/v1/worker/gpu/buffer_utils.py`, UvaBuffer) —
V1-движок требует Unified Virtual Addressing режим, которого нет на этой связке карта+драйвер.
Проверено на маленькой Qwen3-0.6B, то есть дело не в памяти. Медиана 83 мс из ADR-004 была
получена на 5090 через vLLM — на 2070 этот путь закрыт. Дополнительно: `fastjev-serve` вообще
не выставляет vLLM-бекенд (только torch/mlx/llama-cpp/exl3; vLLM — только SDK).

## Ловушки этого хоста

- **`device_ids` в compose не доходит до CUDA под Docker Desktop/WSL2.** Контейнер видит обе
  карты, и порядок нумерации не совпадает с хостом (внутри контейнера 0 = 5070 Ti!).
  Поэтому entrypoint сервиса сам находит 2070 по имени и экспортирует `CUDA_VISIBLE_DEVICES`
  (`docker/jev/entrypoint.sh`, `pick_gpu.py`; для llama.cpp-варианта — по UUID,
  `pin_gpu_uuid.sh`). Блок `deploy.resources.reservations.devices` в compose оставлен: он
  корректен на нативном Linux.
- **Готовое колесо llama-cpp-python (cu124) умирает с SIGILL** на Ryzen 9 5900X (Zen 3, нет
  AVX-512/AVX-VNNI) — и на CPU-пути, и на CUDA-пути, до загрузки модели. Отсюда вариант сборки
  из исходников (`Dockerfile.llamacpp-src`).
- fastjev требует ровно одну видимую CUDA-карту ("Expose exactly one CUDA GPU") — ещё одна
  причина пиновать карту самому.
- `--served-model` обязан содержать `fastjev` и не маскировать Jev-алиасы; обязательны
  `--served-model-description` и `--served-model-release-date`.
- Поле выбранного варианта в ответе System One называется `choice` (не `value`).

## Вывод для C1

Пороги: p95 ≤ 150 мс на 8 вариантов — цель, ≤ 300 мс — порог из ROADMAP §0.

- **Qwen3-0.6B (torch): задержки проходят** (8 вар. p95 160 мс ≈ цель, 16 вар. 233 мс — в
  порог), но качество 0.44 — вдвое ниже целевой 4B. Годится как заглушка C1, не как замена.
- **MiniCPM5-2B (torch): не годится** — 383–778 мс при пороге 300 мс.
- **Qwen3.5-4B на этой карте недостижима** через быстрые пути: vLLM не работает на Turing,
  BF16 не влезает; единственный оставшийся путь — llama.cpp Q4_K_M из исходников (таблица
  выше, TBD до конца замера).
