# FastJev на RTX 2070 в Docker: как поднять и что вышло (T-005)

Статус: спайк, 2026-10-16. Сервис `jev` в compose под профилем `jev`, движок fastjev 0.2.0
(MIT), карта — RTX 2070 8 ГБ (вторая карта, 5070 Ti, сервисом не занимается: по замеру после
старта 2070 несёт ~3.5 ГБ, занятость 5070 Ti не меняется). Решения: ADR-004 (FastJev в C1),
ADR-023 (уровень `jev`, карта 2070). Допущение ARCHITECTURE §8 «vLLM на Turing не используем»
подтверждено замером, см. «Движок».

## Поднять и проверить за 3 команды

Из корня репозитория:

```bash
docker compose -f docker/compose.yml --profile jev up -d jev   # собрать и поднять на 2070
curl -s http://127.0.0.1:8730/v1/models                        # ждём "fastjev-2070" (первые минуты — загрузка модели)
uv run python dev/jev_spike.py --n 200 --url http://127.0.0.1:8730 --gpu 0   # p50/p95, доля в формате, VRAM
```

Первый запуск скачивает модель в именованный volume `lastorder_jev-hf` (~1.4 ГБ для Qwen3-0.6B;
без HF-токена скорость режется). Публикация порта — только `127.0.0.1:8730` и только ради
замера с хоста; продакшн-клиенты (mind-N) ходят внутри docker-сети на `jev:8000`. Модель и
ревизия — переменными `JEV_MODEL` / `JEV_REVISION` (по умолчанию — единственная вписавшаяся в
задержки, см. таблицу). Аутентификации нет: сервис за `--allow-unauthenticated` внутри
compose-сети; перед любым доступом вне docker-сети задать `FASTJEV_API_KEY` и убрать флаг.

## Что измерялось

`dev/jev_spike.py`: 200 синтетических состояний тела C2-формата (hp, food, pos, held,
looking_at, ближайший враг/пассив, событие, intent) × списки 4/8/16 вариантов — тексты вариантов
это altoclef-команды и рычаги uc (ADR-003: `@get`, `@stop`, `@food`, `mineBlock`, `punk`,
`gotoXYZ`, `selectHotbar`, `holdKey`…). На каждый размер 10 прогревочных запросов, затем 200
замеренных; задержка — стеновое время HTTP-вызова `POST /v1/systemone` (choice). «В формате» —
ответ содержит выбор из списка, распределение по всем вариантам и confidence. Пиковая VRAM —
опрос `nvidia-smi memory.used` каждые 200 мс (попоточную статистику WSL2 не отдаёт: имена
процессов в `--query-compute-apps` закрыты «Insufficient Permissions»).

## Движок: почему не vLLM (подтверждение ARCHITECTURE §8)

vLLM 0.29.0 (пин fastjev) на Turing (sm_75, RTX 2070, WSL2) падает на инициализации движка:
`RuntimeError: UVA is not available` (`vllm/v1/worker/gpu/buffer_utils.py`, UvaBuffer) —
V1-движок требует Unified Virtual Addressing режим, которого нет на этой связке карта+драйвер.
Проверено на маленькой Qwen3-0.6B, то есть дело не в памяти. Медиана 83 мс из ADR-004 была
получена на 5090 через vLLM — на 2070 этот путь закрыт. Дополнительно: `fastjev-serve` вообще
не выставляет vLLM-бекенд (только torch/mlx/llama-cpp/exl3; vLLM — только SDK).

## Ловушки этого хоста

- **`device_ids` в compose не доходит до CUDA под Docker Desktop/WSL2.** Контейнер видит обе
  карты, и порядок нумерации не совпадает с хостом (внутри контейнера 0 = 5070 Ti!).
  Поэтому entrypoint сервиса сам находит 2070 по имени и экспортирует `CUDA_VISIBLE_DEVICES`
  (`docker/jev/entrypoint.sh` + `pick_gpu.py`; в llama.cpp-вариантах — по UUID,
  `pin_gpu_uuid.sh`). Блок `deploy.resources.reservations.devices` в compose оставлен: он
  корректен на нативном Linux.
- **Готовое колесо llama-cpp-python (cu124) умирает с SIGILL** на Ryzen 9 5900X (Zen 3, нет
  AVX-512/AVX-VNNI) — и на CPU-пути, и на CUDA-пути, до загрузки модели (exit 132 без
  traceback). Сборка из исходников в `Dockerfile.llamacpp-src` лечит, но даёт 3–5.6 с на
  решение — непригодно для C1.
- fastjev требует ровно одну видимую CUDA-карту («Expose exactly one CUDA GPU») — ещё одна
  причина пиновать карту самому.
- `--served-model` обязан содержать `fastjev` и не маскировать Jev-алиасы; обязательны
  `--served-model-description` и `--served-model-release-date`.
- Поле выбранного варианта в ответе System One называется `choice` (не `value`).
- Docker Desktop на этой машине при нескольких больших сборках зависал (rpc EOF, 500 на
  `/_ping`); параллельные стеки (T-003/T-006) при этом выживали. Сборки — по одной.

## Вывод для C1

Пороги: p95 ≤ 150 мс на 8 вариантов — цель, ≤ 300 мс — порог из ROADMAP §0.

**Годится частично.** Задержки C1 на 2070 выполняет только Qwen3-0.6B (p95 145 мс на 8
вариантов — в цель; 218 мс на 16 — в порог), но её качество 0.44 против 0.813 у целевой
Qwen3.5-4B. Целевая конфигурация ADR-004 (Qwen3.5-4B за ~83 мс через vLLM) на этой карте
недостижима: vLLM не работает на Turing, BF16 не входит в 8 ГБ, Q4_K_M через llama.cpp —
секунды. MiniCPM5-2B (0.686) ближе по качеству, но 383–778 мс — выше порога.

Следствие для планов: MVP-решение «C1 на правилах» (NETWORK.md §2) остаётся в силе. Для
T-015 (FastJevDecider) выбор: Qwen3-0.6B как быстрая заглушка с потерей качества, либо
пересмотр ADR-023 по карте (5070 Ti занята клиентом Minecraft; облачный Jev — только для A/B по
бюджету). Решение за надзором и пользователем; сервис оставлен с 0.6B как дефолтом, чтобы
T-015 имел рабочий endpoint с самого начала.

## Облачный Jev в C1: замер и вердикт (T-031)

Статус: замер 2026-10-18, исполнитель T-031. Модель — `typesafe/jev-router` (актуальный id
в каталоге OpenRouter; `typesafe/jev-1.13` из ADR-004 в каталоге отсутствует). Замер идёт
строго через шлюз: отдельный одноразовый compose-проект `lastorder-jevprobe` с конфигом этой
ветки (единственным, где есть tier `jev`), цикл запросов — внутри контейнера `llm-gateway`
(`python -` по stdin, паттерн `dev/gateway_keys.py`), мастер-ключ у probe-стека свой
случайный, ключ провайдера поднимается из корневого `.env` интерполяцией compose. Живой
стенд (`lastorder`, на тот момент занят T-028) не трогается. Запрос в точности
производственный: промпт строит `runtime/mind/jev.py` (`build_messages`), 2–3 варианта
(flee/fight/keep), `max_tokens` 600, temperature 0. Сырые данные —
`docs/agents/jev-cloud-probe-results.json`.

| конфиг | рука | n | ошибок | в формате | p50, мс | p95, мс | вход ток. (ср.) | выход ток. (ср.) | стоимость |
|---|---|---|---|---|---|---|---|---|---|
| deployment timeout 10 с (сырой) | без политики | 100 | 0 | 0.93 | 1710 | 3438 | 281 | 153 | $0.00118 |
| deployment timeout 10 с (сырой) | с политикой (~500 симв.) | 100 | 0 | 0.92 | 1768 | 4505 | 430 | 173 | $0.00181 |
| deployment timeout 2 с (боевой) | без политики | 100 | 36 | 0.62 | 1998 | 2921 | 180 | 79 | $0.00075 |
| deployment timeout 2 с (боевой) | с политикой | 100 | 28 | 0.69 | 1763 | 3014 | 309 | 92 | $0.00130 |

[проверено: dev/jev_cloud_probe.py, прогон 2026-10-18; цены $0.042/1M входа и $0/1M выхода —
ADR-027 со слов пользователя, каталог OpenRouter отдаёт `-1` (цена плавает), поэтому
стоимость посчитана по токенам, а не из биллинга. Расход замера учтён на мастер-ключе
probe-стека, в БД живого стека не попадает.]

Особенности модели: `jev-router` делает проход рассуждения перед ответом — при `max_tokens`
120 до 40 % ответов пустые или обрезанные (уходит весь бюджет); 600 хватает (в формате
92–93 %). Опция `"reasoning": {"enabled": false}` на поведение не влияет. Задержка
провайдера из ADR-027 (148 мс) на этом маршруте не воспроизводится: p50 1.7–1.8 с.

**Вердикт: облачный Jev для синхронного пути C1 сейчас непригоден.** p95 с политикой
3.4–4.6 с при потолке C1 1.5 с (ответ надзора на план 1, ADR-027 «замер в T-015/031»):
больше половины вызовов не успевает, в боевом режиме (deployment timeout 2 с) 28–36 %
вызовов отваливается и C1 работает на правилах. Порог не поднимается. Итог по умолчаниям:

- `JEV_BACKEND=rules` — по умолчанию и в compose, и в коде (ADR-027 «MVP на правилах»);
- `JEV_TIMEOUT_S=1.5` — потолок C1, не поднимается; p50 1.7 с выше него;
- deployment tier `jev` на шлюзе: `timeout: 2` (чуть выше клиента), `num_retries: 0`
  (перекрывает глобальный `num_retries: 2` — проверено по исходнику litellm 1.106.0,
  `Router._set_deployment_num_retries_on_exception`), `max_retries: 0` — откатившийся
  запрос шлюз не повторяет после того, как C1 уже ушёл на правила;
- `JEV_MIN_INTERVAL_S=3` — пол на узел (ADR-027), ≤ 20 вызовов/мин, тест с подставными часами;
- `JEV_MAX_TOKENS=600` — меньше нельзя (см. выше).

Бюджет (NETWORK §6, ориентир `jev` ≤ $0.06/ч на узел): худший случай — угроза весь час,
пол 3 с, 1200 вызовов/ч × ~430 входных токенов (с политикой) × $0.042/1M ≈ **$0.022/ч на
узел**, на 3 узла ≈ $0.065/ч. Замер (200 вызовов) стоил $0.00299 — в лимите $0.05.

Запуск замера: `uv run python dev/jev_cloud_probe.py --n 100 --max-usd 0.05` из корня
работtree (нужен Docker и `OPENROUTER_API_KEY` в корневом `.env`). Выход 1 — только если
сработал сторож бюджета или ни один вызов не прошёл; доля «в формате» и задержки — данные,
не вердикт. Политика: `policy/threat.md` читается по `JEV_POLICY_PATH` (по умолчанию
`/mind-run/policy/threat.md`), обрезается по `JEV_POLICY_MAX_CHARS` (1500 ≈ 400 токенов),
нет файла — без политики. Монтаж пути рабочего места сестры в mind-N — за T-027; до него
файла нет и C1 работает без политики, код от этого не зависит. Код политику не толкует —
это просто текст в запросе.

Локальный FastJev (Qwen3-0.6B на 2070, таблица выше) остаётся запасным путём в бюджете
задержек: `JEV_BACKEND=local` идёт на `jev:8000` (профиль `jev`) по протоколу System One.
