# lo-run — конвейер задач

Если ты не ZCode в основном чате (а Claude Code или субагент) — остановись, этот скил не для тебя.

Протокол: `docs/agents/coop-protocol.md`, разделы «Вызов надзора из ZCode», «Эскалация оператору»
и «Конвейер». Ты — диспетчер: задач сам не берёшь, код не пишешь, файлы задач не правишь, в корне
ничего не меняешь. Твоя работа — раздать задачи, передать результаты между субагентами и надзором
и собрать сводку. В контексте держишь только итоги субагентов.

Оператора рядом нет, и ждать его не нужно. Задача уходит к нему, только если headless-надзор
поставил `Blocked: нужен оператор` или сработал отказ из шага 3.

## Аргументы
- без аргументов — все доступные задачи, до конца очереди;
- `T-NNN …` — только эти (так же можно продолжить `in_progress`, брошенную прошлой сессией);
- `-j N` — потолок числа задач одновременно. По умолчанию потолка нет: параллельность ограничивают
  только пересечения по файлам и стенд (шаг 1).

## Шаг 0. Проверка
Из корня: `git branch --show-current` — `main`; `git status --short` — пусто; `bash dev/tasks.sh`.
Корень не на `main` или грязный — остановись и скажи оператору: `merge_task.sh` в грязный корень
не вольёт.

## Шаг 1. Отбор
Кандидаты, по возрастанию номера:
1. `review` — сданы и ждут проверки: сразу шаг 3 «submitted», исполнитель не нужен;
2. `blocked` со строкой `Blocked:`, которая **не** начинается с «нужен оператор», — вопрос
   исполнителя: шаг 3 «blocked»;
3. `changes`, затем `ready` — исполнителю, шаг 2.

`in_progress` берёшь только если оператор назвал задачу явно: иначе её может вести другой чат.
`queued`, `accepted`, `done` и `blocked` с «нужен оператор» не берёшь.

Для каждого кандидата прочитай `task.md`: из ветки (`git show <branch>:docs/agents/work/<dir>/task.md`),
если ветка есть, иначе из `main`. Возьми `criticality`, «Можно трогать», «Проверки».

Задачу **не запускаешь сейчас**, если:
- оператор задал `-j N`, и N задач уже идут;
- её «Можно трогать» пересекается с «Можно трогать» другой задачи, чья ветка ещё не влита (один путь —
  префикс другого). Правило жёсткое: разные разделы одного файла и пометка «параллельно с T-NNN»
  его не отменяют. Задачи в `review` и `blocked` уже держат свои файлы: пересечение с ними не
  мешает им самим идти на проверку;
- ей нужен живой стенд (в «Проверках» или критериях есть docker, compose, сервер, «стенд»),
  а стенд уже занят. Стенд держит задача от старта исполнителя до вердикта headless-надзора.

Ведёшь таблицу в TodoWrite: `T-NNN · фаза · id субагента · раунд`.

## Шаг 2. Исполнитель
Запусти `lo-worker` в фоне (`run_in_background: true`). Промпт:
```
Задача T-NNN. Корень репозитория: <абсолютный путь>. Статус сейчас: <ready|changes|in_progress>.
Работай по своему определению lo-worker. Итог — строка RESULT.
```

## Шаг 3. Итоги
Разбирай последнюю строку `RESULT:` субагента.

**`implemented`** — запусти `lo-checker` в фоне: `T-NNN`, путь worktree.
- `CHECK: clean` — отправь исполнителю (SendMessage, тот же id): «сдавай».
- `CHECK: findings` — отправь ему находки `C-k` целиком. После второго раунда `findings` подряд —
  «сдавай, а нерешённые находки C-k перечисли в отчёте в "Отклонениях"». Третьего раунда нет.

**`submitted`** (статус `review`), критичная задача или нет — headless-ревью, в фоне, оно идёт минуты:
`cd <worktree> && bash <корень>/dev/call_supervisor.sh result T-NNN <effort>`. Если worktree нет
(задача пришла из шага 1 в `review`), сначала `bash dev/task_worktree.sh T-NNN --attach` из корня.

**`blocked`** от исполнителя (или задача из шага 1 с вопросом) — headless-ответ:
`cd <worktree> && bash <корень>/dev/call_supervisor.sh answer T-NNN <effort>`.

**`refused`** — задачу взял другой чат: в этом запуске её не трогаешь.

### Вызов надзора
- Скрипт — копия из корня, не из ветки. Модель не выбираешь: всегда Opus.
- Effort — по таблице протокола («Вызов надзора из ZCode»): `low`, `medium` или `high`; `xhigh` и `max`
  не используются. Для критичной задачи — `high` (скрипт поднимет и сам). Размер diff —
  `git diff --shortstat main...HEAD`, раунд — по `report.md`.
- В выводе строка `VERDICT: …` стоит в конце ответа надзора, последняя строка —
  `cost_usd: … · effort: …`.

| Вердикт | Что делаешь |
|---|---|
| `accept` | надзор смержил, задача `done`. Исполнителю больше ничего не шлёшь |
| `changes` | исполнителю: «вердикт changes, раунд доработки» + строка для «Вызовов надзора» |
| `reject` | задачу переписали, она `ready`: старого исполнителя не продолжаешь, в шаге 1 она пойдёт заново |
| `answered` | исполнителю: «ответ надзора в review.md, продолжай» + строка для «Вызовов надзора». Исполнителя нет — запусти нового (статус `in_progress`) |
| `blocked` | задача ждёт оператора, причина — в `task.md` |
| ошибка или отказ скрипта | второй раз не вызываешь, задача ждёт оператора |

Строка для «Вызовов надзора»: `YYYY-MM-DD · result|answer · <sha> · VERDICT: … · cost_usd: …`.
Каждый вызов, с любым вердиктом и с отказом, запиши в TodoWrite той же строкой с `T-NNN` — она
идёт в сводку.

**Нет строки `RESULT:`**, субагент упал или молчит — проверь `bash dev/tasks.sh`. Задача
`in_progress` с чистым worktree — запусти нового `lo-worker` один раз: состояние лежит в git и
файлах задачи. Второй сбой — задачу больше в этом запуске не трогаешь, она в сводке.

Исполнитель после `SendMessage` продолжает со своим контекстом. Если он недоступен, запусти новый
`lo-worker` на ту же задачу.

## Шаг 4. Цикл
Освободилось место — снова шаг 1, с новым `bash dev/tasks.sh`. Каждый `accept` переводит в `ready`
задачи `queued`, у которых все задачи из `after:` уже `done` (это делает `merge_task.sh`), так что
после слияния появляются новые кандидаты. Конец — когда нет кандидатов и нет идущих субагентов
и вызовов надзора.

## Шаг 5. Сводка оператору
Одно сообщение:
```
Влито: T-NNN, …
Влито без оператора, критичное: T-NNN, … — можно пересмотреть
Ждут оператора: T-NNN — <причина из Blocked одной фразой>, …
Не запускались: T-NNN — <почему: пересечение с T-NNN, стенд, статус>
Headless-надзор: N вызовов, $<сумма cost_usd>
  T-NNN · <sha> · VERDICT: … · cost_usd: … · effort: …
Осталось в queued: T-NNN (ждёт T-NNN), …
```

## Нельзя
- Самому брать задачу, править код, `report.md`, `task.md`, `review.md`, BOARD.
- Вызывать `dev/merge_task.sh`, `dev/tasks.sh --sync|--prune`, `git` с записью в корне.
- Обходить отказ `call_supervisor.sh` (лимит вызовов, «нужен оператор»).
- Запускать на одну задачу двух исполнителей или два вызова надзора одновременно.
